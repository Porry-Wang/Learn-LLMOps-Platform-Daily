## 为什么（Q5–Q10 要点卡，长版见 day01_answer.md）

**Q5 数副本为什么要按状态过滤**
- 不过滤时，"记录存在但已失败"（Failed 未删 key）的 Pod 被计入实际副本数。
- 差额被低估甚至归零 → 该补不补 → 系统自认达标、实际可用不足。
- 本质是"数对象"与"数可用对象"的区别；K8s 用 Readiness 堵这个坑。
- 核句：存在 ≠ 可用。

**Q6 丢事件后为什么 27 轮全是动作 0**

- 丢事件那轮，`actual` 与 `last_seen` 同步销账，缓存与现实的错位被掩盖。
- 此后 `changed` 恒为空 → 不产生事件 → 不 observe/diff/act。
- 不是"信号被压制"，是产生信号的差异本身永久消失。
- 核句：丢事件的损失不是少一次响应，是失去发现自己出错的信息来源。

**Q7 act 内部重试成功后，外面循环还有什么意义**
- 重试执行的是过去某一刻生成的动作清单，期间新故障看不见、期望值变了照旧执行。
- 循环每轮用最新期望和最新实际重新推导动作，指令永不过期。
- 重试保证"这组动作做完"，循环保证"目标一直成立"。
- 核句：重试忠于动作，循环忠于目标。

**Q8 集合推导式三部件**
- `observed.items()`：提供此刻每个条目的（名字, 状态）键值对。
- `for name, state`：遍历并解包成两个变量；开头的 `name` 决定放入结果的是名字。
- `if state == "Running"`：只保留运行中条目，供 diff 计数和挑删除对象。
- 核句：推导式只收集名字集合，数个数和删谁都是 diff 的事。

**Q9 break 版为什么看不到 💥**
- 扰动发生在第 10/15/20/25/30 轮；break 版第 6 轮终止，这些轮次不存在。
- 巡视后的"什么都不做"= 每轮对比后确认无差额，发现新偏离的能力保留。
- 退出后的"什么都不做"= 从未对比，无法区分"世界没变"和"变了但没人知道"。
- 核句：退出后打印的成功验证的是过去，控制器的职责是未来。

**Q10 "丢事件才行动"和"达标就 break"为什么是同一个错误**
- 两者切断的是同一个机制：发现期望与实际差异的信息来源。
- 共同假设"当前的正确会自行延续"，而分布式系统里现实持续偏离是常态。
- 正确设计同时满足两点：对比不因达标而停止（level-triggered 循环），且不依赖通知必然送达（定期 resync 兜底）。
- 核句：收敛不是退出的理由，通知送达不是可依赖的前提。

## 结论

1. 声明式是一份长期合同：循环的目的不是"跑到达标"，而是永远在岗。
2. 重试忠于动作，循环忠于目标。
3. 状态展示必须由持续核对驱动，不能只靠事件上报；resync 和轮询循环是两条腿。

## 业务映射（PorryLLMOps平台）

- 页面表单（节点数 / 每节点卡数 / 框架 / 容错策略 / 热更新参数）= spec；平台持续采集的 rank 存活、心跳、日志、训练指标 = status。表单是算法同学的愿望，采集是机器的现实，平台两者都不能篡改，只能对比。
- Reconcile Loop 本体 = 容错调度链路：识别问题即 observe + diff（期望 8 个 rank、实活 7 个），去调度即 act（重启缺失 rank、驱逐故障节点）。热更新的"下一次容错生效"控制的是差异传播到动作的时机。
- 价值：算法同学不用理解调度细节即可跑训练、出错免值守；Infra 同学从手动任务运维中被模板化自愈解放。
- 抽错的三种具体坏法：观察值回写用户表单 → 模板被污染；状态只靠上报不持续核对 → 任务挂死时页面仍显示 Running，GPU 白烧；只发现差额不执行动作 → 平台退化为大屏，立项价值不成立。

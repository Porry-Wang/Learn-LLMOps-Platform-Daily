# Day 2 完整梳理：显存与算力账本

---

## 一、三本账的核心公式

### 账本①：模型状态（每卡显存）

**每个参数 16 字节** = 2（BF16 权重）+ 2（BF16 梯度）+ 4（FP32 主权重）+ 4（Adam 动量 m）+ 4（Adam 方差 v）。

**ZeRO 切分规则：**

| Stage | 每卡模型状态 | 切什么 |
| :--- | :--- | :--- |
| ZeRO-0 | `16Ψ / (tp·pp)` | 什么都不切 |
| ZeRO-1 | `(4Ψ + 12Ψ/dp) / (tp·pp)` | 12Ψ（优化器状态）按 dp 切 |
| ZeRO-2 | `(2Ψ + 14Ψ/dp) / (tp·pp)` | 14Ψ（优化器+梯度）按 dp 切 |
| ZeRO-3 | `16Ψ / (tp·pp·dp)` | 全切 |

**核心理解：** 4Ψ（权重+梯度）前向反向每卡都要用完整的一份，不能切；12Ψ 只在更新时用、每参数独立，所以能按 dp 切。**能切的恰恰是“不需要每卡完整”的。**

---

### 账本②：激活（每卡显存）

**单层激活公式：**

| 模式 | 公式 | 说明 |
| :--- | :--- | :--- |
| none | `s·b·h·(34 + 5·a·s/h)` | 34 是线性层（∝s），5as/h 是 attention（∝s²） |
| selective | `s·b·h·34` | 砍掉 s² 项，保留线性层 |
| full | `2·s·b·h` | 只留每层输入 |

**切分规则：** `每卡激活 = 单层激活 × (layers/pp) / tp`

- **PP 决定“这张卡参与几层”**：PP=1 参与全部 80 层，PP=2 参与 40 层。
- **TP 决定“每层被拆几份”**：TP=8 每层只算 1/8 宽度。
- **dp 不切激活**：每卡跑不同 micro-batch，激活天然不同，不存在重复。

**关键权衡：**

| | 留存代价（显存） | 重算代价（算力） | 策略 |
| :--- | :--- | :--- | :--- |
| attention 中间结果（s²） | 大（∝s²） | 小 | **砍掉，重算** |
| 线性层中间结果（34） | 小（∝s） | 大 | **保留，不重算** |

**一句话：selective 砍掉“占显存多但重算便宜”的 attention，保留“占显存少但重算昂贵”的线性层。**

---

### 账本③：算力（训练时长）

**公式：** `C = 6·N·D` FLOPs，full recompute 用 `8·N·D`。

- 6ND = 前向 2ND（1乘+1加）+ 反向 4ND（算输入梯度 2 + 算权重梯度 2）。
- 8ND = 6ND + 重算前向 2ND（full 在反向时把前向重算一遍）。
- **selective 的算力账也是 6ND**（只重算 attention 一小部分，近似为 6ND）。

**单位陷阱：** `n = params_b × 1e9`，`d = tokens_t × 1e12`，两个都要展开成“个”再相乘。

**时长：** `hours = C / (gpus × peak_tflops×1e12 × mfu) / 3600`

---

## 二、两个关键公式的原理

### 气泡占比：`(pp-1)/(m+pp-1)`

**语言解释：** 流水线有 pp 个 stage、m 个 micro-batch。前 pp-1 步是填充阶段（后面的 stage 空等），后 pp-1 步是排空阶段（前面的 stage 空等）。总步数 = m+pp-1，每个 stage 空闲 pp-1 步，所以气泡 = (pp-1)/(m+pp-1)。

**记忆：** m 越大气泡越小，pp 越大气泡越大。`m >= 2pp` 是工程上可接受的气泡上限。

### scan 排序键：`hours / (1 - bubble)`

**为什么不是“显存最小”？** 显存只是**及格线**（不 OOM 才能进候选），不是**优劣标准**。两个配置都不 OOM 时，选**有效时长更短**的。

**`(1-bubble)` 是有效计算时间占比**，所以 `hours/(1-bubble)` 是“折算成无气泡的等效时长”，越小越好。

## 三、案例手推记录

### 案例 1：7B, ZeRO-1, TP=1, PP=1, DP=8, full

```
模型状态：4×7 + 12×7/8 = 28 + 10.5 = 38.5 GB
激活（full）：2×4096×1×4096 = 33.5MB/层 × 32层 / 1 = 1.07 GB
总账：38.5 + 1.07 = 39.57 GB ✅ 放得下
时长：8×7e9×1e12 / (8×989e12×0.4) / 3600 ≈ 4915 小时
```

**教训：** 8 张卡训练 7B 模型 1T token，本来就是几千小时（约 205 天）。手算时长时先看卡数。

### 案例 2：70B, ZeRO-1, TP=8, PP=1, DP=16, selective

```
模型状态：(4×70 + 12×70/16) / (8×1) = (280+52.5)/8 = 41.56 GB
激活（selective）：4096×1×8192×34 = 1.14GB/层 × 80 / 8 = 11.41 GB
总账：41.56 + 11.41 = 52.97 GB ✅ 放得下
时长：6×70e9×1e12 / (128×989e12×0.4) / 3600 ≈ 2304 小时
```

### 案例 2 变式：none 模式

```
单层激活：4096×1×8192×(34+160) = 6.51 GB
每卡激活：6.51 × 80/8 = 65.1 GB
总账：41.56 + 65.1 = 106.66 GB ❌ OOM
```

**结论：none 模式下 s² 项让激活暴涨，OOM。selective 用小于 2ND 的算力换掉 53.7 GB 显存，是最优折中。**

## 四、scan 结果分析

**最优配置：TP=8, PP=1, DP=16, ZeRO-1, selective，52.97 GB，气泡 0%，2304 小时。**

**为什么它排第一？**

1. **PP=1 → 气泡 0%**：唯一气泡为 0 的选择。
2. **TP=8 → 压显存到放得下**：TP 小于 8 则需 PP≥2 才能满足 tp·pp·dp=128，气泡就来了。
3. **selective → 算力账 6ND**：比 full（8ND）快 33%。

**对比：** TP=8, PP=2, DP=8 显存更省（29.77 GB），但气泡 20%，扣气泡后 2880 小时，比第一名慢 25%。**显存不是越省越好。**

- **ZeRO 用通信换显存**（AllGather 把权重拼回来）。
- **recompute 用算力换显存**（反向时重算前向）。

## 七、业务映射：为什么平台必须自己决定并行策略

平台任务表单里，用户只填两个数：**GPU 机器数 × 单机卡数**。用户不填 TP/PP/DP，也不填 ZeRO stage。这不是产品偷懒，而是因为这两个数根本不是同一层的东西。

### 要点 1：用户填的是「资源边界」，平台要交的是「切法」

`16Ψ` 是每个参数的固定开销，但**每张卡实际背多少**，取决于 `tp·pp·dp` 怎么切。同样 8 张卡：

- `TP1 PP1 DP8`：模型不切，8 张卡各跑一份数据副本；
- `TP8 PP1 DP1`：模型宽度切 8 份，只有一份数据副本。

前者能训 7B，后者才可能装下 70B；两者的吞吐、通信量、故障域完全不同。用户知道自己「要 8 张卡」，但通常不知道自己的模型有多少个 head、能不能被 8 整除。**把「资源」翻译成「并行策略」是平台的责任，不是用户的作业。**

### 要点 2：机器形状决定 TP 上限，这不是偏好而是物理约束

TP 在每一层内部做 All-Reduce/All-Gather，通信频率最高，必须待在 NVLink 域里。**一台 8 卡机器就是一个 NVLink 域，所以 `tp <= 单机卡数`。**跨机 TP 不是绝对不能跑，而是会掉 MFU、把账算坏，所以在准入阶段就该拒绝或标红。

PP 只在 stage 边界传激活，可以跨机；DP 本来就是跨机复制。**「8 卡一台」真正限制的是 TP，不是 PP/DP。**这也解释了为什么平台拿到「机器数 × 单机卡数」后，必须先看单机卡数，再看总卡数。

### 要点 3：OOM 是门槛，吞吐才是分数

以 70B / 128 卡为例，两个方案都「能跑」：

| 方案 | 每卡显存 | 有效时长 | 说明 |
| --- | ---: | ---: | --- |
| TP8 PP1 DP16 + ZeRO-1 + selective | 52.97 GB | 2304 h | top-1 |
| TP4 PP1 DP32 + ZeRO-1 + full | 77.90 GB | 3072 h | 也放得下，但多烧 2ND |

如果平台只检查「是否 OOM」，它会认为两个都合格，甚至可能随机挑一个。**但第二个方案慢 33%。**平台的价值在于：先拿显存做准入门槛，再在可行集合里按 `有效时长 = 纯算力时长 / (1 - 气泡占比)` 排序，并把「为什么选它」写进放置报告。

### 要点 4：放置必须独立于调度

- **调度（scheduler）**回答：什么时候、把 Pod 放到哪台机器。
- **放置（placement）**回答：模型怎么切、每个 rank 是谁、需要什么形状的资源。

混在一起的后果很具体：队列按「卡数」放行，结果 Pod 起来了才发现 TP 超了单机、或者 OOM；或者为了等一个根本不存在的资源形状，任务永远排队。正确顺序是：**容量/放置先算可行性 → 调度按这个形状找资源 → 生命周期按 rank 计划启动。**这也让「同一任务重跑得到同一套 rank」成为可复现的。

### 一句话（核句）

> **用户买的是「几张卡」，平台交付的是「这几张卡怎么切」；切法决定放不放得下、跑得多快、坏了怎么恢复。**

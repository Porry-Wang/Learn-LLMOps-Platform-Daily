## 第一组：理论四问（D1.1）

### Q1｜命令式和声明式的区别？K8s 为什么选声明式？

**30 秒版**

命令式给步骤，声明式给目标。K8s 选声明式，是因为分布式系统里故障是常态：只有把期望状态持久化，控制器才能每轮重新对比、补齐差额，自愈和审计才有依据。

**标准答案（4 点）**

1. **定义差异**：命令式给操作过程（先做 A 再做 B），声明式只写目标结果（我要 3 个副本），过程由系统负责。
2. **合同 vs 指令**：声明式的期望状态持续存在，任何时刻都能据此重新核对；命令式脚本中途失败后，没有记录说明“还差什么”。
3. **故障是常态**：机器会坏、网络会抖、配置会被人改；只有持续对比现实，系统才能收敛和自愈。
4. **产品收益**：用户只提交核心参数，执行复杂度被封装——这正是“页面填表发起训练”这种平台形态成立的前提。

**小例子**

声明式写 `replicas: 3`，实际 2 个：控制器算出差 1，补 1 个。命令式脚本执行到一半失败，没人知道还差几个。

**边界与易错**

- 声明式不是“没有命令”，而是把命令藏进控制器；控制器最终仍要调用创建/删除接口。
- 不是所有场景都适合声明式：一次性、无状态的批处理，命令式更直接。
- 声明式不保证立即收敛，它保证持续尝试；收敛速度取决于循环频率和动作成功率。

**可能追问**

- 问：声明式会不会更慢？答：单次反应可能多一轮观察，但换来可恢复和可审计；故障是常态时，这个交换划算。
- 问：期望状态存在哪里？答：K8s 存在 etcd 的 spec 里；平台里就是任务表单和配置版本。

**核句**

> 命令式是一次性指令，声明式是一份长期合同。

### Q2｜`act()` 有 30% 失败率，为什么系统最终还能收敛到 3 副本？

**30 秒版**

因为循环每轮都从当前现实重新算差额，不依赖上一轮的成功记忆。失败没有改变现实，下一轮差额还在，动作会被重新生成；只要单次成功率非零，持续尝试最终会收敛。

**标准答案（4 点）**

1. **每轮重新观察**：循环不记忆“上次做到哪”，只比较当前期望和当前现实。
2. **失败不改变现实**：动作失败后差额依然存在，下一轮会重新生成同一个动作。
3. **非零成功率**：单次失败只推迟达标，不阻止达标；在独立假设下，连续失败的次数越多，概率越接近 0。
4. **归零即幂等**：差额为 0 时 `diff` 返回空列表，系统什么都不做，做一百遍结果相同。

**小例子**

期望 3、实际 2，创建动作失败率 30%：下一轮仍是 3 vs 2，继续补。连续 10 次都失败的概率是 `0.3^10 ≈ 0.000006`。

**边界与易错**

- 前提是失败真的没有改变现实；如果失败留下“占位但不可用”的半成品，差额要按“可用”算，不能按“存在”算。
- 30% 独立失败是 toy 假设；真实故障可能相关（同一节点、同一网络），非零成功率不等于快速收敛。
- 收敛是概率意义，不是有限步保证；真实系统要加重试上限、退避和告警。

**可能追问**

- 问：如果失败率 100% 呢？答：不收敛；非零成功率是前提。
- 问：失败重试会不会造成风暴？答：会，所以要有退避、限流和熔断；循环本身不解决这个问题。

**核句**

> 单轮失败只推迟达标，阻止不了达标，因为循环每一轮都重新从现实出发。

### Q3｜spec 和 status 为什么要分开？合并成一个字段会出什么问题？

**30 秒版**

spec 是用户写的愿望，status 是控制器写的现实；作者不同、流向单向。合在一起会互相覆盖，也无法表达“期望 3、实际 2”的差额。

**标准答案（4 点）**

1. **作者不同**：spec 只由用户写（意图），status 只由控制器写（观察到的现实）；合成一个字段，两边写入会互相覆盖。
2. **差额是信息**：“期望 3、实际 2”是 reconcile 的驱动力，也是告警和页面状态的数据源；一个字段无法同时表达“要什么”和“有什么”。
3. **流向单向**：控制器按 spec 修正现实，绝不把 status 回写进 spec——观察到的事实（比如实际分配到的节点 IP）不该混进用户模板。
4. **合并即失明**：再也无法区分“用户的愿望”和“当前的现状”，自愈和审计同时失去依据。

**小例子**

`spec.replicas=3`、`status.replicas=2`，差 1，控制器补 1 个。如果只有一个字段，控制器把 2 写回去，下一轮目标就变成了 2，系统永远补不齐。

**边界与易错**

- status 里可以有 `observedGeneration`、conditions 等派生信息；它们属于“现实”，不属于用户模板。
- 用户改 spec 是合法的；控制器改 spec 才是污染（admission/defaulting 是另一层，不算控制器回写）。
- 分开不等于所有字段都要暴露给用户；可以只展示摘要，但底层语义要分开。

**可能追问**

- 问：status 能不能被用户改？答：API 层可能允许，但语义上归控制器；用户改 status 不会改变期望。
- 问：为什么不用事件代替 status？答：事件是流水，status 是当前快照；恢复和展示需要快照。

**核句**

> spec 是愿望，status 是现实，系统的全部工作就是把两者的差额变成动作。

### Q4｜边缘触发丢一个事件后为什么无法自愈？真实系统怎么补救？

**30 秒版**

边缘触发只在收到事件时行动，平时不核对现实。丢一次事件，控制器就失去了这次变化的触发；如果缓存也同步销账，之后连差异都不再产生，系统会永久停在错误状态。补救是定期全量 resync 加差额告警。

**标准答案（4 点）**

1. **只在事件时行动**：edge 不主动轮询，它的世界观由事件流构建。
2. **丢事件即失去触发**：这次变化没有进入控制器的行动路径；它不会主动发现，缺口可能永久不可见。
3. **损失要精确表述**：不是少响应了一次，而是失去了发现出错的手段。
4. **补救是双层**：框架提供的定期全量 resync（informer 按配置周期把对象重新推一遍，强制重新核对，常见是小时级），加上“差额持续不为零则告警”兜住 resync 周期内的静默窗口。

**小例子**

期望 3、实际 2，Pod 死亡事件被丢掉；如果缓存也更新成 2，`changed` 从此为空，控制器再也不会运行。resync 会重新观察一次，发现 3 vs 2，重新触发补建。

**边界与易错**

- edge 不是永远坏；事件不丢时它更快。坏的时候是“你看不见”，不是“它一定错”。
- resync 在 informer/workqueue 框架层，不是业务代码里随手加的定时器。
- 告警只能缩短发现时间，不能替代修复；最终仍要有 reconcile 动作。

**可能追问**

- 问：resync 能不能完全替代事件？答：能兜底但延迟高；事件负责快，resync 负责不漏。
- 问：为什么不在每次事件里全量对账？答：那就变成 level-triggered，edge 省成本的优势消失。

**核句**

> 丢事件丢掉的不是一条通知，是未来任何一天发现自己出错的能力。

## 第二组：代码追问三题（D1.2）

### Q5｜`diff()` 里数 Running 时，如果把状态过滤去掉、直接数 dict 里所有 key，什么场景下会算错？

**30 秒版**

不过滤会把“记录存在但已失败”的 Pod 计入实际副本数，差额被低估甚至归零，该补不补。本质是“数对象”和“数可用对象”的区别；K8s 用 Readiness 区分。

**标准答案（4 点）**

1. **记录有两种**：运行中/可用的，和已失败但记录还没删除的；直接数总数会把后者计入实际数量。
2. **数量被高估**：差额被低估甚至归零，控制器在可用不足时不补建，系统带病且自认为达标。
3. **toy 与真实的差别**：toy 里死亡即删记录，过滤暂时等价于不过滤；扩展成“失败标记不删除”后才显形。
4. **K8s 的做法**：用 Readiness 表达这个区分，Deployment 统计 Ready 副本数，不是 Pod 对象总数。

**小例子**

期望 3；有 3 个 Pod 记录，其中 1 个 Failed。过滤后实际 2，补 1 个；不过滤实际 3，不动作，但 Service 只有 2 个可用端点。

**边界与易错**

- 如果失败 Pod 会被立即删除，过滤确实暂时没有差别；不能因此说过滤没用。
- 可用性不只看 Running：还有 Ready、readiness probe、Terminating 等状态。
- 不同业务对“可用”的定义不同；平台要把这个语义显式化，不能靠状态字符串猜。

**可能追问**

- 问：为什么 `phase=Running` 还不够？答：Running 不等于 Ready；进程活着但可能没准备好接流量。
- 问：Terminating 算不算可用？答：通常不算；要看业务是否允许优雅退出期间继续接流量。

**核句**

> 数对象和数可用对象是两个数字，把“存在”当成“可用”是状态失真的经典源头。

### Q6｜edge 实验里 Pod 明明死了，为什么后面 27 轮都是「动作 0」？把因果链一步步讲出来。

**30 秒版**

edge 版只在 `changed` 非空时运行。丢事件那轮，Pod 死亡和 `last_seen` 销账同时发生，缓存与现实一致，`changed` 从此为空；没有事件就没有 observe/diff/act，于是 27 轮全是动作 0。desired 与 actual 的缺口一直在，只是没人看。

**标准答案（4 点）**

1. **控制器不直接看世界**：它只在现实与记录出现差异时被触发，这个差异就是 `changed`。
2. **丢事件那轮**：Pod 死亡与记录销账同时发生，`changed` 不再产生；缓存与现实一致，但 desired 与 actual 的缺口还在。
3. **静默成为永久**：无 `changed` → 无事件 → 无 observe/diff/act；世界也没有新变化，系统停在 0/3。
4. **对照**：若只删现实不删记录，差异持续存在，事件即使迟到也能让系统自愈；致命的不是迟到，是掩盖。

**小例子**

30 轮实验，第 3 轮死亡事件被丢；第 4–30 轮的 `changed` 都是空列表，动作数为 0，最终 0/3。若缓存仍记着 3，下一轮 diff 会持续报差，系统会恢复。

**边界与易错**

- 这是 toy 的“一致错位”建模；真实 informer 丢 watch 事件会由 re-list/resync 兜底。
- 27 轮是实验设定，不是固定数字；关键是“没有新事件”这个状态。
- 不要把“desired vs actual 的缺口”和“cache vs actual 的 `changed`”混为一谈；两者不是同一个差异。

**可能追问**

- 问：为什么不是“信号被压制”？答：没有任何信号被压制；产生信号的差异对比根本没发生。
- 问：真实系统怎么避免？答：watch 断点续传（resourceVersion）+ 定期 resync + 差额告警。

**核句**

> 27 轮不是信号被压制，是产生信号的物理过程已不存在。

### Q7｜如果把 `act()` 改成「失败就自动重试直到成功」，外面那个循环还有什么存在意义？

**30 秒版**

重试保的是“这份动作清单最终执行成功”，循环保的是“目标一直成立”。重试期间世界会变：新故障不在旧清单上，期望也可能被改；只有外层循环每轮重新观察、重新推导，指令才不过期。

**标准答案（4 点）**

1. **对象不同**：重试对“动作”，循环对“目标”。
2. **条件会变**：重试期间可能出现新故障，用户也可能改期望；旧清单不会自动包含这些变化。
3. **循环重新推导**：每轮用最新期望和最新现实生成动作，指令永远基于当前信息。
4. **差别不在次数**：不是“多试几次”的问题，是“信息来源”的问题；重试只看旧清单，循环看世界。

**小例子**

期望 3、实际 2；重试正在创建 Pod A。期间 Pod B 死了，用户把期望改成 4。重试仍只创建 A；外层循环下一轮看到 4 vs 2，再补 2 个。

**边界与易错**

- 重试仍有价值：处理瞬时失败、减少循环空转；但不能替代循环。
- 重试要有上限、退避和幂等保证；无限重试会卡死循环。
- 循环频率要匹配收敛速度；太快浪费，太慢恢复慢。

**可能追问**

- 问：那能不能只在循环里重试？答：可以，但重试逻辑仍要基于最新观察；本质还是循环。
- 问：重试和幂等什么关系？答：幂等让重试安全；不幂等的动作重试会重复副作用。

**核句**

> 重试忠于动作清单，循环忠于目标与现实。

## 第三组：词汇检查（D1.3）

### Q8｜集合推导式 `{name for name, state in observed.items() if state == "Running"}` 的三部件各干什么？

**30 秒版**

`observed.items()` 提供（名字，状态）键值对；`for name, state` 解包；`if state == "Running"` 过滤；开头的 `name` 决定结果放名字。它只负责收集名字集合，计数和删除是 `diff` 的事。

**标准答案（4 点）**

1. **`observed.items()`**：提供此刻每个条目的（名字，状态）键值对，已删除的不包含。
2. **`for name, state in ...`**：把每对解包成两个变量，逐个遍历。
3. **`if state == "Running"`**：只保留运行中的条目。
4. **开头的 `name`**：决定放入结果的是名字而不是状态；结果集合供 `diff` 计数差额、挑选删除对象。

**小例子**

`{"a": "Running", "b": "Failed", "c": "Running"}` → `{"a", "c"}`，长度 2；`b` 被过滤掉。

**边界与易错**

- 集合无序；需要稳定顺序时用列表或排序。
- 过滤条件要和“可用”语义一致；Running 不一定 Ready。
- 不要在遍历字典时修改字典；先收集，再删除。

**可能追问**

- 问：为什么用集合不用列表？答：去重 + O(1) 成员判断；代价是丢顺序。
- 问：如果两个 Pod 同名？答：K8s 名字唯一；toy 用 dict 也保证唯一。

**核句**

> 推导式四零件各管各的——从哪拿、怎么拆、留什么、装什么进结果。

## 第四组：动手实验的两个口头解释（D1.4–D1.5）

### Q9｜（D1.4）把 `pass` 改成 `break`、跑 `--disturbance 5` 后，为什么日志里根本看不到 💥 那行？

**30 秒版**

扰动在第 10/15/20/25/30 轮，break 版第 6 轮就退出了，那些轮次根本没发生，所以日志里没有 💥。结尾的 ✅ 3/3 只验证退出那一刻，不证明之后还能保持。

**标准答案（4 点）**

1. **轮次没到**：扰动设定在第 10/15/20/25/30 轮；break 版第 6 轮终止，程序没运行到那些轮次。
2. **成功只描述瞬间**：最终打印的 ✅ 3/3 是真实的，但它只描述退出瞬间，与“之后保持 3/3”没有逻辑关系。
3. **两种“什么都不做”**：巡视后的“什么都不做”是每轮对比、确认无差额；退出后的“什么都不做”从未做过对比。
4. **真实系统**：控制器退出后，不存在任何实体知道“应该 3 个、现在几个”，故障将无日志、无告警地发生。

**小例子**

break 版第 6 轮退出；第 10–30 轮的 5 次扰动全部没有发生，日志里 💥 为 0。巡视版跑满 30 轮，5 次扰动都在下一轮被修复。

**边界与易错**

- break 版不是“造假”；它只是把观测窗口截短了。
- 如果任务本来就有明确终点（一次性 Job），退出是合理的；长期运行的控制器不能类比。
- “退出时 3/3”与“未来保持 3/3”是两个命题，不能互相证明。

**可能追问**

- 问：那什么时候可以退出？答：目标是一次性完成且不再需要保证时；长期系统不能。
- 问：怎么证明“之后也能保持”？答：只能靠持续运行/定期核对；退出后的打印证明不了。

**核句**

> 退出后打印的成功验证的是过去，控制器的职责是未来——两者没有逻辑关系。

### Q10｜（D1.5）「丢事件就下班」和「达标就 break」为什么是同一个错误的两种写法？

**30 秒版**

两者都让“实际持续符合期望”失去保证：break 是主动放弃对比，丢事件是被动掩盖差异。共同假设是“正确会自行延续”，而分布式系统里现实持续偏离才是常态。

**标准答案（4 点）**

1. **后果层**：两者都让“实际持续符合期望”失去保证。
2. **机制层**：切断的是同一个东西——发现差异的信息来源；break 是主动放弃对比，丢事件是被动掩盖差异。
3. **共同假设**：“正确会自行延续”；而分布式系统里现实持续偏离才是常态，两者都失去了验证该假设的手段。
4. **正确设计**：对比不因达标而停止（level-triggered），发现不完全依赖通知送达（resync 兜底）。

**小例子**

break 版在第 6 轮 3/3 后退出；edge 版在第 3 轮丢事件后停在 0/3。两者之后都发生了“本该被发现”的偏离，但都没有机制去发现。

**边界与易错**

- 两者不是“同一行代码”，是同一类设计错误；面试时要说清共同点和区别。
- 一次性任务可以 break；长期控制器不行。
- resync 能救丢事件，但救不了已经退出的进程；机制不同，不能混答。

**可能追问**

- 问：哪个更危险？答：丢事件更隐蔽；break 至少是显式选择。
- 问：resync 能救 break 吗？答：不能；进程退出了，resync 也没人执行。

**核句**

> 达标退出和只等报信是同一种赌法——赌世界不会在你不在场时改变。

## 第五组：业务映射（D1.6）

### Q11｜Reconcile Loop 这套机制在 PorryLLMOps 平台里对应什么功能？给算法/Infra 同学解决什么痛点？如果这层抽错了会怎样？

**30 秒版**

平台表单是 spec，采集的 rank 存活、心跳、指标是 status，容错调度链路就是 controller：发现少 rank 就重启，发现坏节点就驱逐。价值是算法同学不用理解调度细节、出错免值守；Infra 从手动运维里解放。

**标准答案（4 点）**

1. **界面层**：页面填参数 = 写期望状态；平台采集 rank 存活、心跳、日志、指标 = 读实际状态。
2. **机制本体**：容错调度链路就是循环本身——识别问题（对比差额）+ 修复动作（重启缺失 rank、驱逐故障节点、按容错策略拉起）。
3. **热更新**：“下一次容错生效”说明 spec 变更靠这个循环传播进运行中任务，产品概念直接映射机制。
4. **抽错的三种坏法**：观察值回写用户模板（作者混淆）；状态只靠上报不做持续核对（页面显示运行中而实际挂死，GPU 空烧）；发现差额无修复动作（退化为大屏，值守没被解放）。

**小例子**

期望 8 个 rank、实活 7 个，差 1，重启缺失 rank；某节点故障，驱逐并重新调度。页面显示 Running 的依据是 status，不是“提交成功”这个动作。

**边界与易错**

- 平台不是 K8s 的复制品；它管训练任务、rank、checkpoint、配额，对象和动作都不同。
- “免值守”不是“永不出错”，是出错能被发现和修复。
- 热更新有生效时机；不是所有参数都能热改，有的要重启任务。

**可能追问**

- 问：和 K8s 的 controller 有什么区别？答：对象不同（训练任务/rank vs Pod），动作不同（重启 rank、回滚 checkpoint、驱逐节点），但循环范式相同。
- 问：平台最容易被抽错成什么？答：大屏——只展示状态，不执行修复。

**核句**

> 平台卖的不是提交任务那一刻，是提交之后几千小时里每一次偏离都被发现和纠正。

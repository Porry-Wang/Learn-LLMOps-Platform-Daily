# **第一组：理论四问（D1.1）**

**第 1 题 ✅ 补充一个更深的原因**

你说的「用户只给目标、复杂过程内部封装」是对的。但面试里能加分的是另一层：**声明式让「期望状态」成为一份持久存在的、可以被任何人随时查阅的账本**。命令式脚本执行完就结束了，如果第 7 步失败，没人知道该从哪补救；而声明式下期望状态一直写在那儿，任何 controller、任何时刻、哪怕重启了，都能重新对比、重新逼近。这才是「自愈」的根基。

一句话记住：**命令式是一次性指令，声明式是长期合同。**



**第 2 题 ✅ 完全正确**

再帮你把话说得更锋利一点：30% 失败率不影响收敛，是因为**每一轮 diff 都重新从「当前实际」算起，失败的动作下一轮会被重新算出来、重新执行**。这有个名字叫**幂等**——做一遍和做十遍，只要目标达到就没有副作用。面试里说出「level-triggered + 幂等」这两个词，这题就是满分。



**第 3 题 ❌ 有一个方向性错误**

你说「status 变化之后又会影响 spec」——**恰恰相反，status 永远不会回写 spec**。这是本题的核心：

```txt
   spec   ← 只有用户/上游 controller 写（「我要 3 副本」）  = 愿望
   status ← 只有本 controller 写   （「现在活着 2 个」）    = 现实

   两个字段、两个作者、单向流动。reconcile 的本质 = 对比 spec 和 status 的差。
```

为什么要分开？给你三个能写进面试的理由：

1. **作者不同**：spec 是用户的意图，controller 无权篡改用户的愿望。如果合并，controller 一旦「纠正」了字段，用户想要的东西就被抹掉了。
2. **偏差本身就是信息**：「spec 说要 3 个，status 显示 2 个」这个差额正是驱动系统的燃料，也是告警、看板、排队诊断的证据源。合并成一个字段，「没达标」这个状态就无法表达——你没法用同一个字段同时说「要什么」和「有什么」。
3. **并发写会打架**：用户随时可能 `kubectl apply` 更新 spec，controller 持续心跳更新 status。分开放，各自的写互不覆盖。

顺带一个和你复习笔记里「Infra 和算法的衔接——机器 IP」同类的边界提醒：**网络归属、IP 分配这类事实属于 status（观察到的现实），绝不该让算法同学写进 spec（他的愿望）。** 抽错方向的 CRD 就是烂 CRD——这正好是 §0.0 说的「抽象的正确性」。



**第 4 题 —— 现在讲透，今天动手时你会亲手验证它**

边缘触发（edge-triggered）的运作方式是：**只在收到「状态变化事件」时才行动，平时根本不看实际状态。**

丢事件后无法自愈的因果链是这样的：

```txt
   pod-2 挂了 → 死亡事件在网络上丢了 → controller 从没看见
   ↓
   controller 的触发条件是「有新事件」，没有事件 = 不行动
   ↓
   它永远不会去对比「期望 3 / 实际 2」这个差额
   ↓
   差额存在，但无人知晓 → 系统安静地坏下去，直到永远
```

对比一下就明白了：level-triggered 每一轮都重新观察实际状态，所以就算某个动作失败、某个事件丢失，**下一轮照样能发现差额**。edge-triggered 省了轮询的开销，<u>代价是把「事件流完整」当成了前提</u>——而分布式系统里网络会分区、进程会重启、订阅会断线（DDIA 第 8 章的四个必然麻烦之一），这个前提必然被打破。

真实系统的补救就是你该背下来的答案：**定期全量 resync**。K8s 的 informer 默认每隔一段时间（`resyncPeriod`，典型 12 小时）把所有对象重新推一遍，等价于「假装收到了一次全量事件」，强制 controller 重新对比期望与实际。这就是 edge-triggered 的效率 + level-triggered 的兜底，两者结合的产物。



# **第二组：代码追问三题（读完/跑完代码后答）**



Q5：统计当前副本数时必须按状态过滤，因为记录存在两种：Pod 正常运行，以及 Pod 已失败但记录尚未删除。直接数记录总数会把失败的算作运行中，使实际数量"看起来"达到期望值，控制器因此不再创建新 Pod，而真正可用的副本不足。本质区别是"数对象"和"数可用对象"。K8s 用 Readiness 状态表达这一点：Deployment 统计的是 Ready 副本数，不是 Pod 对象总数。

Q6：控制器不主动查看真实世界，只在实际状态与它上一次收到的通知出现差异时才会被触发，这个差异就是事件。丢事件那一轮，Pod 死亡的同时，这一变化没有进入控制器的缓存——代码里体现为 actual 和 last_seen 同步移除了该 Pod。此后真实状态与控制器掌握的记录始终一致，不再产生任何差异，也就再无事件触发；控制器不行动，世界也就不再发生别的改变。所以丢失事件造成的损失不是"少了一次响应"，而是差异本身永久消失——控制器失去了发现自己出错的信息来源。

Q7：重试解决的是"让某个动作最终成功"，循环解决的是"让目标最终成立"，二者不等价。重试的依据是过去某一刻生成的动作清单，而清单生效期间条件会继续变化：可能出现新的故障，期望值也可能被用户从 3 改成 2——按旧清单执行就会多创建一个。循环每轮都依据最新的期望和最新的实际重新推导该做什么，动作永远基于当前信息。一句话概括差异：重试的输入是动作清单，循环的输入是目标与现实。

# 第四组：动手实验的两个口头解释（D1.4-1.5）

Q9 ：💥 行由扰动逻辑打印，扰动发生在第 10、15、20、25、30 轮。break 版在第 6 轮（第一次满足"无差额且超过 5 轮"）就终止了循环，程序根本没有运行到第 10 轮，所以后续四次扰动从未发生，日志里自然看不到。它最终仍打印"✅ 3/3"，因为退出那一刻确实满足期望——这个成功是真实的，但只在第 6 轮之前有效。两者的差别：巡视后的"什么都不做"，是每一轮都重新对比期望与实际、确认无差额之后的结果，发现新偏离的能力被完整保留；退出后的"什么都不做"，是没有做过任何对比——它无法区分"世界没有变化"和"世界变化了我不知道"，前者是事实，后者是假设。

Q10 ：两者是同一个错误的两种写法，因为切断的是同一个机制——发现期望与实际之间差异的信息来源。"达标就 break"的逻辑是：此刻无差异，所以以后也不必再看；"丢事件才行动、且事件可丢"的逻辑是：只在差异被通知时才发现，而差异被掩盖后通知永远不会再来。共同的前提假设是"当前的正确会自行延续"，而分布式系统中现实持续偏离（节点故障、进程被杀）恰恰是常态，两种做法都失去了验证这个假设的手段。因此正确的设计必须同时满足两点：对比行为不因达标而停止（level-triggered 的循环），且对比行为不依赖通知一定送达（resync 兜底）。



# 第五组：业务映射（D1.6，两三句话）

Reconcile Loop 在PorryLLMOps平台对应的是「任务提交 + 实时监控 + 自动容错」这一整条链路背后的持续核对机制：用户在页面填写的作业模板构成期望状态，平台采集的 rank 存活、心跳与训练指标构成实际状态，容错调度就是不断对比两者差额并执行修复动作（重启缺失 rank、驱逐故障节点、按热更新策略带新参数拉起）。它给算法同学解决的是"不用理解调度细节也能把训练跑起来、出错不用人守"，给 Infra 解决的是"重复的任务运维被平台模板化，人力从值守里解放"。抽错的后果不是不便而是误导：把观察值写回用户配置会污染模板；状态只靠事件上报、不做持续核对，页面会在任务实际挂死时仍显示运行中，让算法同学白等、GPU 白烧；只发现差额不执行动作，平台退化为大屏，立项价值不成立。

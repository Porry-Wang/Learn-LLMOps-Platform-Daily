# **第一组：理论四问（D1.1）**

Q1： 命令式 vs 声明式，K8s 为什么选声明式

① 命令式给出操作过程（先做 A 再做 B），声明式只写目标结果（我要 3 个副本），过程由系统自己负责。

② 声明式下期望状态作为"合同"持续存在，任何时刻、任何进程都能依据它重新核对和执行；命令式脚本一旦中途失败，没有任何记录说明"还差什么"。

③ K8s 选声明式的根本原因是故障是常态：只有把目标持久化，系统才可能持续逼近，自愈能力建立在这份持久化之上。

④ 附带收益是使用面收窄：用户只提交核心参数，执行复杂度被封装——这正是"页面上填表发起训练"这种平台形态能成立的前提。 

核句：命令式是一次性指令，声明式是一份长期合同。



Q2： act 有 30% 失败率，为什么系统还能收敛 

① 循环每一轮都从当前现实重新计算"差多少"，不依赖也不记忆上一轮的成功失败。

② 失败的动作没有改变现实，所以下一轮对比时差额依然存在，动作会被重新生成、重新执行。 

③ 只要每个动作有非零成功概率，差额就只会缩小不会凭空扩大，若干轮后必然归零。

④ 差额归零后 diff 返回空列表，系统什么都不做且做一百遍结果相同——这个性质叫幂等。 

核句：单轮失败只推迟达标，阻止不了达标，因为循环每一轮都重新从现实出发。



Q3： spec 和 status 为什么要分开 

① 作者不同：spec 只由用户写（意图），status 只由控制器写（观察到的现实）；合成一个字段，两边的写入会互相覆盖。 

② 差额本身是信息："期望 3、实际 2"是 reconcile 的驱动力，也是告警和页面状态的数据源；一个字段无法同时表达"要什么"和"有什么"。 

③ 流向单向：控制器按 spec 修正现实，绝不把 status 回写进 spec——观察到的事实（比如实际分配到的节点 IP）不该混进用户的模板。 

④ 合并即失明：再也无法区分"用户的愿望"和"当前的现状"，自愈和审计同时失去依据。 

核句：spec 是愿望，status 是现实，系统的全部工作就是把两者的差额变成动作。



Q4： 边缘触发丢事件后为什么无法自愈，真实系统怎么补救 

① 边缘触发只在收到事件时才行动，平时不核对现实，它的世界观完全由事件流构建。 

② 事件丢失意味着这次变化没有进入控制器的记录，此后记录与现实处于"一致的错位"——不再有新的差异，就再也产生不了通知，系统永久停在错误状态。

 ③ 损失要精确表述：不是少响应了一次，而是失去了发现出错的手段。

 ④ 补救是双层：框架内置定期全量 resync（informer 周期性把所有对象重新推一遍，强制重新核对，小时级），加上"差额持续不为零则告警"兜住 resync 周期内的静默窗口。 

核句：丢事件丢掉的不是一条通知，是未来任何一天发现自己出错的能力。



# **第二组：代码追问三题（读完/跑完代码后答）**

Q5： 状态过滤去掉会什么场景算错 

① Pod 记录存在两种：运行中的，和已失败但记录未删除的；直接数总数会把后者计入实际数量。 

② 数量被高估后差额被低估甚至归零，控制器在可用不足时不补建，系统带病且自认为达标。 

③ 今天的 toy 代码死亡即删记录，过滤暂时等价于不过滤；危害在扩展成"失败标记不删除"后才显形。 

④ K8s 用 Readiness 表达这个区分：Deployment 统计 Ready 副本数，不是 Pod 对象总数。 

核句：数对象和数可用对象是两个数字，把"存在"当成"可用"是状态失真的经典源头。



Q6： edge 版 0/3 静默 27 轮的因果链 

① 控制器不直接看世界，只在现实与它的记录出现差异时被触发，这个差异就是事件。 

② 丢事件那轮，Pod 死亡与记录销账同时发生，此后记录与现实恒"一致"，差异不再产生。 

③ 无差异则无事件，无事件则无动作；控制器不动作，世界也无新变化，静默成为永久状态。 

④ 对照：若只删现实不删记录，差异持续存在、事件迟到送达、系统会自愈——致命的不是迟到，是掩盖。 

核句：27 轮不是信号被压制，是产生信号的物理过程已不存在。



Q7 act 改成失败必重试，循环还有什么意义

① 重试保"某个动作最终成功"，循环保"目标最终成立"，两者对象不同。 

② 重试期间条件继续变化：新故障不在旧清单上；期望被改成 2 时，旧清单仍会多补一个。 

③ 循环每轮依据最新期望和最新现实重新推导动作，指令永远基于当前信息。 

④ 所以循环不能被"内部重试"替代——差别不在尝试次数，在信息来源。 

核句：重试忠于动作清单，循环忠于目标与现实。



# **第三组：词汇检查**

Q8： 集合推导式三部件 

① observed.items() 提供此刻每个条目的（名字，状态）键值对，已删除的不包含。 

② for name, state in ... 把每对解包成两个变量。 

③ if state == "Running" 只保留运行中的条目。 

④ 开头的 name 决定放入结果的是名字而非状态；结果集合供 diff 计数差额、挑选删除对象。 

核句：推导式四零件各管各的——从哪拿、怎么拆、留什么、装什么进结果。



# 第四组：动手实验的两个口头解释（D1.4-1.5）

Q9： 为什么 break 版日志里没有 💥

① 扰动设定在第 10/15/20/25/30 轮；break 版第 6 轮终止，程序没运行到那些轮次，扰动从未发生。 

② 最终打印的 ✅ 3/3 也是真实的，但它只描述退出瞬间，与"之后保持 3/3"没有逻辑关系。 

③ 巡视后的"什么都不做"是每轮对比、确认无差额的结果，发现新偏离的能力保留；退出后的"什么都不做"没做过任何对比。 

④ 搬到真实系统：控制器退出后，不存在任何实体知道"应该 3 个、现在几个"，故障将无日志、无告警地发生。 

核句：退出后打印的成功验证的是过去，控制器的职责是未来——两者没有逻辑关系。



Q10： 丢事件就下班与达标就 break 为何是同一个错误 

① 后果层：两者都让"实际持续符合期望"失去保证。 

② 机制层：切断的是同一个东西——发现差异的信息来源；break 是主动放弃对比，丢事件是被动掩盖差异。 

③ 共同假设是"正确会自行延续"，而分布式系统中现实持续偏离才是常态，两者都失去了验证该假设的手段。 

④ 正确设计同时补两点：对比不因达标而停止（level-triggered），发现不完全依赖通知送达（resync 兜底）。 

核句：达标退出和只等报信是同一种赌法——赌世界不会在你不在场时改变。



# 第五组：业务映射（D1.6，两三句话）

Q11 Reconcile Loop 在PorryLLMOps平台对应什么 

① 界面层：页面填参数 = 写期望状态，平台采集 rank 存活/心跳/指标 = 读实际状态；这是"清楚设置参数、清楚了解状态"的痛点来源。 

② 机制本体：容错调度链路就是循环本身——识别问题（对比差额）+ 修复动作（重启缺失 rank、驱逐故障节点、按容错策略拉起）。 

③ 热更新的"下一次容错生效"说明 spec 变更靠这个循环传播进运行中任务，产品概念直接映射机制。 

④ 抽错的三种具体坏法：观察值回写用户模板（作者混淆）、状态只靠上报不做持续核对（页面显示运行中而实际挂死，GPU 空烧）、发现差额无修复动作（退化为大屏，值守没被解放）。 

核句：平台卖的不是提交任务那一刻，是提交之后几千小时里每一次偏离都被发现和纠正。

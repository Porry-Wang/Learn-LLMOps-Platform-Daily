## 第一组：基础账本（Q1–Q5）

### Q1｜`16Ψ` 的 16 是哪五项加起来的？为什么 FP16 训练反而比 BF16 更容易溢出？

**30 秒版**

16 字节 = BF16 权重 2 + BF16 梯度 2 + FP32 主权重 4 + Adam m 4 + Adam v 4。FP16 的问题是 5 位指数、动态范围窄，大梯度容易溢出；BF16 用 8 位指数换范围，再用 FP32 主权重补精度。

**标准答案（4 点）**

1. **16 字节 = 5 项之和**：BF16 权重 2 + BF16 梯度 2 + FP32 主权重 4 + Adam 动量 m 4 + Adam 方差 v 4。
2. **为什么要 FP32 主权重**：BF16 尾数只有 7 位，参数更新量很小时会被舍入掉；更新用 FP32 那份，更新完再转回 BF16 给前向。
3. **FP16 输在指数范围**：FP16 只有 5 位指数，最大约 65504，大梯度、大激活容易溢出成 inf；BF16 有 8 位指数，范围和 FP32 同级（约 3.4e38）。
4. **代价是精度**：BF16 尾数比 FP16 少，所以训练常用“BF16 权重/梯度 + FP32 主权重”的组合，用 16 字节/参数换稳定。

**小例子**

7B 模型，模型状态总量是 `16 × 7 = 112 GB`；ZeRO-1、dp=8 时每卡 `(4×7 + 12×7/8) = 38.5 GB`。FP16 能表示的最大值约 65504，超过这个量级会溢出；实际训练会用 loss scaling 缓解。

**边界与易错**

- 16 字节是“Adam + 混合精度训练”的口径；推理只需约 2 字节/参数（BF16 权重），另外还有 KV cache。
- FP16 配合 loss scaling 也能训练；BF16 的优势是更宽容，不是绝对更好。
- 优化器状态可以用 8-bit 量化，那时每参数不再是 16 字节；面试要先说口径。

**可能追问**

- 问：为什么不用纯 FP32 训练？答：显存和带宽翻倍，算力也更贵；混合精度是性价比。
- 问：BF16 精度低会不会影响收敛？答：主权重和优化器状态是 FP32；BF16 只用于前向/反向的计算和存储。

**核句**

> 16 字节买的是稳定训练；FP16 输在指数范围，不是精度。

### Q2｜激活公式里 34 和 `5as/h` 分别对应什么？为什么 attention 那一项和 `s²` 成正比？

**30 秒版**

34 是线性项，`5as/h` 是 attention 的平方项。分数矩阵是 `a×s×s`，每个分数存 5 字节，所以有 `5as²b` 字节；除以 `sbh` 就是 `5as/h`。`s²` 来自 QK^T，序列翻倍这项变 4 倍。

**标准答案（4 点）**

1. **34 是线性项**：所有随 `s·b·h` 线性增长的激活，包括 attention 的输入、QKV 投影、输出投影，以及 MLP 的输入、4h 中间层、激活缓存、输出。按 Megatron 论文口径可粗拆成 attention 线性 10 + MLP 线性 24。
2. **`5as/h` 是 attention 平方项**：每个 head 的分数矩阵是 `s×s`，每个分数存 5 字节（分数 2 + softmax 输出 2 + dropout mask 1），总计 `5·a·s²·b` 字节；除以 `s·b·h` 后写成 `5as/h`。
3. **`s²` 从 QK^T 来**：每个 query token 都要和每个 key token 算相似度，所以分数表是 `s×s`；序列翻倍，这一项变 4 倍。
4. **selective 的取舍**：`s²` 项占显存多、重算便宜，砍掉；34 项占得少、重算贵，保留。单层从 `sbh(34+5as/h)` 降到 `34sbh`，算力账仍近似 6ND；full 只留 `2sbh`，但算力变 8ND。

**小例子**

`s=4096, b=1, h=8192, a=64`：`5as/h = 5×64×4096/8192 = 160`。单层 none 是 `4096×8192×194 ≈ 6.51 GB`；selective 是 `4096×8192×34 ≈ 1.14 GB`。

**边界与易错**

- 34 不是物理常数，会随实现、融合算子、mask 保留策略变化；论文口径只是近似。
- 每个分数 5 字节也是论文口径；FlashAttention 不显式物化完整分数矩阵，实际激活更低。
- selective 不是“不算 attention”，而是反向时重算；算力账仍略高于 6ND。

**可能追问**

- 问：为什么 attention 的 `s²` 不按 dp 切？答：激活按 PP/TP 切；dp 每卡跑不同数据，激活天然不同，没有重复可省。
- 问：FlashAttention 之后这个公式还成立吗？答：它减少 HBM 读写和不显式存矩阵，实际激活更低；公式可当上界/口径。

**核句**

> 34 是线性项，`5as/h` 是 `s²` 项；selective 砍“占得多、重算便宜”的 attention，保“占得少、重算贵”的线性层。

### Q3｜ZeRO-3 相比 ZeRO-1 省了多少显存、多了多少通信？为什么通信是 1.5×？

**30 秒版**

ZeRO-3 把权重、梯度、优化器状态全按 dp 切，比 ZeRO-1 多省 `4Ψ(1-1/dp)/(tp·pp)`；代价是每步通信从约 2Ψ 变 3Ψ，1.5×。它省模型状态，不省激活。

**标准答案（4 点）**

1. **公式对比**：ZeRO-1 每卡模型状态是 `(4Ψ + 12Ψ/dp)/(tp·pp)`；ZeRO-3 是 `16Ψ/(tp·pp·dp)`。
2. **省下的显存**：两者相减，省 `4Ψ(1-1/dp)/(tp·pp)`。dp 越大，越接近省掉一整份 4Ψ（权重+梯度）。
3. **通信为什么 1.5×**：ZeRO-1 每步约 2Ψ（梯度 reduce-scatter + 权重 all-gather）；ZeRO-3 每步约 3Ψ（前向前 all-gather 权重、反向前再 all-gather、反向后 reduce-scatter 梯度），3/2 = 1.5。
4. **边界**：ZeRO-3 只省模型状态，不省激活；dp=1 时没有分片可切，收益接近 0，反而多通信。

**小例子**

7B、tp=pp=1、dp=8：ZeRO-1 是 38.5 GB，ZeRO-3 是 14 GB，省 24.5 GB；通信从 2 个单位变 3 个单位。

**边界与易错**

- ZeRO-3 每次前向都要把权重 all-gather 回来，延迟敏感；不是“显存越省越好”。
- 长序列下激活可能才是大头，ZeRO-3 省不了激活，别答错对象。
- FSDP 是 ZeRO-3 风格的实现；分片组通常就是 dp 组。

**可能追问**

- 问：ZeRO-2 和 ZeRO-3 差在哪？答：ZeRO-2 切梯度和优化器状态，权重仍复制；ZeRO-3 连权重也切。
- 问：什么时候不该用 ZeRO-3？答：dp 小、模型放得下、通信瓶颈明显时。

**核句**

> ZeRO-3 用 1.5× 通信换掉最后一份 4Ψ 复制；省的是模型状态，不是激活。

### Q4｜为什么 TP 一般不超过 8？用 reconcile 视角说明「跨机 TP」会让哪本账变难看。

**30 秒版**

TP 每层都要 All-Reduce/All-Gather，通信频率最高，必须待在 NVLink 域；一台 8 卡机通常就是一个域，所以 `tp≤8`。跨机 TP 能跑，但走 IB、掉 MFU，还把故障域从一台扩到一组。

**标准答案（4 点）**

1. **通信频率最高**：TP 在每层内部做 All-Reduce/All-Gather，前向和反向都同步；DP 只在梯度更新时通信，频率低一个量级。
2. **NVLink 域是物理边界**：一台 8 卡机器通常就是一个 NVLink 域，卡间带宽远高于跨机网络；TP 超过单机卡数就要走 InfiniBand，带宽降、延迟升，MFU 明显掉。
3. **跨机 TP 不是绝对不能跑**：有 NVLink 交换机或多机互联方案时可以，但成本和复杂度高；`tp <= 单机卡数` 是工程约束，不是物理定律。
4. **reconcile 视角**：一个 TP 组是一个不可分割的逻辑副本；跨机后副本横跨多台机器，任意一台故障，整组一起重启，故障域从“一台”变成“一组”。平台要维护跨机 gang 的期望状态，容量账、故障账、重试账都会变复杂。

**小例子**

70B/128 卡：`TP8 PP1 DP16` 是 52.97 GB、2304 h；若强行 `TP16`，就要跨两台机器走 IB，本模型不把它列为候选。

**边界与易错**

- NVLink 域不一定等于 8；NVSwitch、GH200 等方案可以更大，那时 TP 可以超过 8。
- TP≤8 是常见工程规则，不是绝对上限；面试要说“通常/本课程约束”。
- PP/DP 可以跨机；受限制的主要是 TP，不要把三者混在一起说。

**可能追问**

- 问：TP 和 DP 的通信差多少？答：TP 每层 all-reduce/all-gather，DP 每步梯度 all-reduce/reduce-scatter；频率差一个量级。
- 问：TP=16 一定不能用吗？答：能跑，但需要跨机高速互联；成本和 MFU 要实测。

**核句**

> TP 的通信在每一层，必须待在 NVLink 域；8 卡一台是物理边界，不是拍脑袋。

### Q5｜手算：1000 张 H100、7B、1T token、MFU 0.4，训练要多久？单位陷阱在哪？

**30 秒版**

`6ND`，N=7e9，D=1e12，C=4.2e22 FLOPs；1000×H100×0.4 MFU 约 3.956e17 FLOP/s；约 29.5 小时。这是纯算力下界，不含气泡、通信、数据加载和故障。

**标准答案（4 点）**

1. **公式**：`C = 6ND`；`hours = C/(gpus × peak_tflops × 1e12 × mfu)/3600`。
2. **单位陷阱**：N=7B=7e9 个参数，D=1T=1e12 个 token；`N×D=7e21`，不是 7。B 和 T 之间差 `1e18`，先展开成“个”再相乘。
3. **代入**：`C = 6×7e9×1e12 = 4.2e22` FLOPs；有效算力 `1000×989e12×0.4 = 3.956e17` FLOP/s；时间 `4.2e22/3.956e17 ≈ 1.062e5` 秒 ≈ 29.5 小时。
4. **这是下界**：没计 PP 气泡、TP/DP 通信、数据加载、故障重启；1000 卡也不是典型 2 的幂拓扑。

**小例子**

同样是 7B/1T：8 张 H100 约 3686 小时（约 154 天）；1000 张约 29.5 小时。这个模型里，时长随卡数线性下降——但真实系统会被通信和故障拖慢。

**边界与易错**

- 6ND 是普通训练；full recompute 用 8ND，慢 33%。
- MFU 0.4 是假设；真实大集群的 MFU 可能更低，拓扑和 straggler 都会影响。
- 29.5 小时只是算力账，不能承诺端到端交付时间。

**可能追问**

- 问：为什么不是 2ND？答：反向约 4ND，加前向 2ND 等于 6ND。
- 问：29.5 小时能端到端跑完吗？答：不能保证；还要加通信、气泡、checkpoint 和故障恢复。

**核句**

> `6ND` 先把 B 和 T 展开成“个”，再除以卡数×峰值×MFU；29.5 小时是下界。

## 第二组：平台边界（Q6）

### Q6｜平台表单只收「机器数 × 单机卡数」，切法由 Infra 写进启动脚本。平台应该提供什么信息、做哪些校验？

**30 秒版**

平台不替 Infra 决定 TP/PP/DP/ZeRO。平台给资源画像、容量计算和准入校验；Infra 把切法写进脚本。平台负责拦住跑不了的、解释跑得慢的、留下可复盘的证据。

**标准答案（4 点）**

1. **资源画像**：单机卡数、GPU 型号与 HBM、NVLink 域、可用机器数、队列/配额、拓扑与亲和性；这些是 Infra 做并行决策的输入。
2. **容量计算与准入校验**：把三本账做成计算器，Infra 填完 TP/PP/DP/ZeRO 后算出每卡显存、气泡、有效时长；提交时校验 `tp·pp·dp = 总卡数`、`tp ≤ 单机卡数`、`tp | heads`、`pp ≤ layers`、`m ≥ 2pp`、不 OOM。坏配置在提交时拒绝。
3. **切法归 Infra**：模型结构、训练框架、通信拓扑、是否 recompute，Infra 最清楚；平台不应偷偷改写脚本。切法必须显式、可复现、责任清晰。
4. **记录与证据**：保存配置版本、放置方案、rank 映射、事件时间线；失败时能回答“当时为什么这么切、哪本账超了”，而不是只剩一个“运行失败”。

**小例子**

16×8、70B：平台算出 `TP8 PP1 DP16 + selective` 是 52.97 GB、2304 h；`TP4 PP1 DP32 + full` 是 77.90 GB、3072 h。Infra 选；平台校验 `8×1×16=128`、`8≤8`、`8|64`、`1≤80`、`m≥2`、不 OOM。

**边界与易错**

- 平台可以给候选和推荐，但不能悄悄改 Infra 的脚本；自动放置也要可解释、可覆盖、可审计。
- 资源画像不是用户填的越多越好；NVLink 域、拓扑要靠平台发现，不能靠猜。
- 只查 OOM 不够；慢 33% 的配置也“能跑”，但不是好配置。

**可能追问**

- 问：那平台为什么还要学三本账？答：能校验、能解释、能排障、能翻译（8 卡一台 → TP 上限 8）。
- 问：Infra 写错了怎么办？答：提交时拒绝并给出具体原因；运行时记录实际放置，事后可复盘。

**核句**

> 切法由 Infra 写，平台把资源和后果算清楚：提交前拦住跑不了的，运行时暴露跑得慢的，事后留下可复盘的证据。

## 第三组：排序与准入（Q7）

### Q7｜`--scan` 的排序键为什么不能是「是否 OOM」？

**30 秒版**

OOM 只是二元门槛，能进候选的都不 OOM；真正要比的是有效时长 `hours/(1-bubble)`。70B 的 TP8+selective 比 TP4+full 快 33%，两者都不 OOM；只按 OOM 排序会把慢的当合格。

**标准答案（4 点）**

1. **OOM 是二元门槛**：只回答“能不能跑”，不回答“跑得快不快”；能进候选的都不 OOM，再拿它排序没有区分度。
2. **可行集合里要比吞吐**：两个都不 OOM 的配置可能差 30% 以上；要选更快的，不是“刚好能跑”的。
3. **排序键**：`effective_hours = hours/(1-bubble)`。`hours` 是纯算力时长，`1-bubble` 是有效计算占比；相除是“折算成无气泡的等效时长”，越小越快。同分再按小 TP、小 PP、省显存 tie-break。
4. **反例**：70B/128 卡，`TP8 PP1 DP16 + selective` 是 52.97 GB、2304 h；`TP4 PP1 DP32 + full` 是 77.90 GB、3072 h。两者都不 OOM，后者慢 33%。

**小例子**

同一条 70B/128 卡任务，显存从 52.97 GB 涨到 77.90 GB，时间从 2304 h 涨到 3072 h；多出来的 768 小时就是“只查 OOM”会漏掉的代价。

**边界与易错**

- `effective_hours` 仍是启发式：它没给 TP/ZeRO 通信定价，真实排序要结合实测 MFU。
- 气泡模型假设 stage 均匀；真实 PP 可能负载不均，气泡会更大。
- 显存不是完全没用：它决定能不能放下，也会影响多任务打包；只是不该当主排序键。

**可能追问**

- 问：为什么同分按小 TP、小 PP？答：通信和故障域更小；这是 tie-break，不是主排序。
- 问：显存最省什么时候重要？答：当它决定能不能放下，或影响多任务打包和碎片时。

**核句**

> OOM 是及格线，吞吐才是分数；先筛掉 OOM 的，再在及格线里选有效时长最短的。

### A1｜公式速查

```
模型状态：ZeRO-0 16Ψ/(tp·pp)
          ZeRO-1 (4Ψ + 12Ψ/dp)/(tp·pp)
          ZeRO-2 (2Ψ + 14Ψ/dp)/(tp·pp)
          ZeRO-3 16Ψ/(tp·pp·dp)

单层激活：none sbh(34 + 5as/h)
          selective 34sbh
          full 2sbh

每卡激活：单层激活 × layers / pp / tp（不除 dp）

训练算力：6ND；full recompute 8ND
训练时长：C / (gpus × peak_tflops × 1e12 × mfu) / 3600
气泡占比：(pp - 1) / (m + pp - 1)
有效时长：hours / (1 - bubble)
```

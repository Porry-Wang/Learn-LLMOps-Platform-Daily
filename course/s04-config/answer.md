## 第一组：字段与优先级

### Q1｜五组字段，哪几组改变容器形状？

**S｜我遇到的情况**

第一次看创建页，我的直觉是「字段太多」。跑 `translate.py` 第一段时我数了一下：登记了 35 个字段，但真正改变容器形状的只有 9 个——其余的不是分类信息，就是采集/通知策略。

**T｜我要解决的问题**

页面为什么分成这五块？每一块到底谁负责？「不改变容器形状」的字段为什么还要存？

**A｜我做了什么**

1. **按责任切组**：

   | 组 | 用户填什么 | 平台拿它干什么 | 进容器？ |
   | --- | --- | --- | --- |
   | 任务身份 | 阶段 / 名称 / 类型 / 描述 / 场景 / 标签 | 分类、校验、检索、通知策略 | 否 |
   | 训练程序 | 框架 / 配置文件 / Git / init / start / stop | 跑什么代码、怎么起 | 是 |
   | 训练输入 | 基座模型 / tokenizer / 数据集 / 数据地址 | 解析成路径并注入 | 是 |
   | 执行环境与资源 | 镜像 / 依赖 / env / 资源池 / GPU 型号 / 机器数×卡数 / 挂载 | 生成容器规格 | 是 |
   | 运行保障与观测 | 算力检测 / 容错 / 指标 / 轨迹 / 通知 / 推送 | 采集与告警 | 否 |

2. **区分「不进容器」和「不重要」**：身份组决定校验规则、可选框架、通知对象；保障组决定采集哪些指标、失败怎么处理。它们不进容器，但决定这次运行**被怎么对待**。
3. **标出一个真实误区**：「调试任务」是任务分类（影响配额/通知），「Debug 模式」会改变启动流程（九图第 3 节明确区分）。这两个混在一起，就解释不了「为什么同一个任务行为不一样」。

**R｜结果**

演示脚本第 1 段直接打印「全部字段 / 进容器字段」，35 → 9 这个对比一眼可见；`FIELD_GROUPS` 登记清单，`EXECUTED_FIELDS` 标出真正翻译的部分。

**可能被追问**

- 身份字段真的完全不影响运行吗？——不确定，九图自己也把这条列成待核实项（可能影响可选框架、校验、通知）。本 toy 只登记、不实现，回答时要主动说这是边界。
- 为什么保障组不进容器？——它改变的是「平台怎么观测这次运行」，不是「容器长什么样」；算力检测可能在启动前跑，也不进训练容器。

**核句**

> 页面长不是因为字段多，是因为它在同时回答五类责任；只有三类责任会改变容器的形状。

### Q2｜四层优先级，为什么平台注入最高？

**S｜我遇到的情况**

配 S3 时，`cv` 里每个字段都带一个来源层；这次要把「冲突时谁赢」讲成一句话。我先按直觉排了「用户 > 模板 > 平台」，然后被镜像摘要打脸：如果用户能覆盖 digest，平台固定的安全边界就没了。

**T｜我要解决的问题**

同一个参数出现在多处时，有没有一个确定、可复算的赢家？

**A｜我做了什么**

1. **定顺序**：`template < task < run_override < platform_injected`（`config.py:121`）。
2. **给每层一个例子**：模板 `lr=3e-4`、任务 `max_steps=8000`、本次改 `lr=1e-4`、平台注入 `image_digest=sha256:…`。
3. **定 `None` 规则**：`None` 等于「这层没写」，不覆盖上层（`test_none_does_not_override_lower_layer`）。否则用户清空一个下拉框会把模板值也清掉。
4. **解释为什么 injected 最高**：镜像摘要是安全边界，用户可以用自己的镜像，但不能绕过平台固定 digest；`build_runtime_spec` 把摘要拼成 `repo@sha256:…`，有摘要就不看浮动 tag。

**R｜结果**

`test_four_layers_precedence` 里四层都写 `lr`，最终值取最高层、`sources` 也记最高层；`translate.log` 第 2 段同一张表能看出四个字段分别被哪层拿下。

**可能被追问**

- 真实系统有六层，为什么砍成四层？——层数越多，「为什么没生效」越难答；先把「冲突谁赢 + 来源可查」讲清，比背六层名字有用。第 5–6 层（启动命令、热更新）在 Day 8 单独讲。
- 用户改了镜像但平台注入 digest，会怎样？——`image` 用用户的，`digest` 用平台的，拼成 `user-image@digest`；如果 digest 对不上，启动直接失败——这是有意的（宁可失败，不可漂移）。

**核句**

> 优先级不是「谁大谁小」，是「谁能被审计、谁必须不能被动」——镜像摘要属于后者。

### Q3｜`sources` 与内容哈希

**S｜我遇到的情况**

CLI 里每行参数后面都有 `← run_override`。一开始我以为这只是好看，直到有人问「这个 lr 到底谁定的」，我把那一行指给他看——三秒钟结案。

**T｜我要解决的问题**

怎么在不存四份副本的前提下，回答「这个值从哪来」？内容哈希又该算哪些字段？

**A｜我做了什么**

1. **`sources[key] = 赢家层名`**：`merge_config` 边合并边记（`config.py:129`），`ConfigVersion` 冻结时一起存。
2. **用它做三件事**：CLI 输出 `← 来源`；复盘时区分「用户填错」和「平台注入旧值」；冲突排查时先看赢家是谁。
3. **哈希只算执行字段**：`NON_EXECUTION_KEYS` 排除 `name / description / comment / tags`，改备注不产生新版本（`test_comment_does_not_change_content_hash`；`translate.log` 第 7 段两个哈希相同）。
4. **说清代价**：`merged + sources` 只保留**赢家**，丢失了「落败层想设什么」。要看「为什么没生效」的完整历史，得靠请求日志 / 事件；这是拿空间换的取舍，不是缺陷。

**R｜结果**

`cv-0001-7d6e6deb` 的 9 个字段每个都有来源；同一个配置重复提交，哈希不变、`cv` 复用；改 `lr` 或改 token 都会产生新 `cv`。

**可能被追问**

- 改了 `hf_token` 会产生新版本吗？——会，连接串变了执行就不同。哈希不可逆，不泄露明文；但如果在意，可以对 secret 字段做 HMAC。
- 为什么不用四层原始 dict + 运行时再算？——那样每次查来源都要重放合并，且一旦合并逻辑升级，历史结果可能变；存赢家是「当时的事实」。

**核句**

> `sources` 记的是「谁赢了」，不是「大家都想写什么」——前者够破案，后者要另存审计流。

## 第二组：四问与注入

### Q4｜三条路径的四问

**S｜我遇到的情况**

我原以为「数据集地址」就是一个字符串，填进去就行。`translate.py` 第 3 段把四问答完，我才发现它要经过四次转手：表单 → 合并后的 cv → 环境变量 → 训练代码自己的读取逻辑。任何一步断了，用户看到的现象都是「数据没找到」。

**T｜我要解决的问题**

三条最常出问题的路径，各自怎么走完全程？

**A｜我做了什么**

1. **数据路径**：表单「训练数据集」→ `merged['data_path']`（没填按 task 推导 `s3://porry-data/<task>`）→ `PORRY_DATA_PATH` + 挂载 `/data` → 训练脚本自己读。
2. **产物路径**：表单「产出存储目录」→ `merged['ckpt_path']`（没填按 `task/run/attempt` 推导）→ `PORRY_CKPT_PATH` + 挂载 `/ckpt` → 框架的 `save_checkpoint`；平台之后从这里采集 Artifact。
3. **指标路径**：表单「TensorBoard 路径」→ `merged['tf_events_path']`（默认落在 ckpt 同目录）→ `PORRY_TF_EVENTS_PATH` → `SummaryWriter`；平台轮询该目录出曲线。
4. **写成结构化数据**：`FIELD_TRACE`（`config.py:179`）+ `trace()`（`:219`），每项都带 where / stored / injected / read 四个键；测试逐字段断言四问都答全。

**R｜结果**

`logs/translate.log` 第 3 段每个字段都打四行；`trace("ckpt_path", merged, sources)` 还会带上当前值和来源（没填时 `source=derived`）。

**可能被追问**

- 为什么指标路径默认放 ckpt 目录下？——一次运行一个目录，采集和清理都以 run 为单位；真实系统还要考虑容量和保留策略。
- 同一份配置重试，产物路径会不会撞？——不会，路径里有 `attempt`；这也是 S3 里 Artifact 自带 attempt 的原因。

**核句**

> 路径不是「一个字符串」，是「四次转手」；用户报「数据没找到」时，先定位断在哪一次。

### Q5｜init 的 `export` 为什么传不到 start

**S｜我遇到的情况**

演示第 5 段我故意在 init 里写 `export HTTP_PROXY=…`，然后在 start 的环境里查——`False`。这不是我造的坑，是真实平台里最常见的「本地能跑、平台不行」。

**T｜我要解决的问题**

为什么两个命令不能共享 shell 状态？正确的做法有哪几条？

**A｜我做了什么**

1. **看实现**：`render_commands()`（`config.py:430`）把 init 和 start 渲染成两次独立的 `sh -c`——两个进程，环境只从平台注入。
2. **确认边界**：`build_runtime_spec` 的 `env` 只来自「平台注入 + 用户 env 字段」，**不回读**上一个进程的 shell；`test_init_export_does_not_reach_start` 钉住。
3. **给出两条正路**：写进配置的 `env` 字段（进 merged、进哈希、能溯源）；或者直接写进 `start_cmd`。
4. **点出隐蔽做法**：init 把变量写进共享卷里的文件、start 再 source——能跑，但耦合不可见、不可审计，不建议当默认方案。

**R｜结果**

演示输出里 `init` 与 `start` 两条命令并列，`HTTP_PROXY` 在 `spec.env` 中不存在；平台侧回答「为什么变量没生效」有了确定答案。

**可能被追问**

- K8s 的 initContainer 不是同一个 Pod 吗？——同一个 Pod，但 initContainer 与主容器**环境不共享**，只共享 volume；Docker 的 ENTRYPOINT/CMD 也是独立进程。shell 状态从来不跨进程。
- 那平台能不能替用户把 init 的 export 解析出来？——可以（解析 shell 是脏活），但不该默认做：变量应该显式声明在配置里，才能进哈希和溯源。

**核句**

> 两个 `sh -c` 就是两个进程；`export` 只活在它自己的 shell 里，平台不替用户猜。

### Q6｜为什么有 WORLD_SIZE 没有 RANK

**S｜我遇到的情况**

第一版 RuntimeSpec 里我顺手塞了 `RANK`。写完自检时发现一个荒谬的事实：一份配置只有一个 `RANK` 值，可这次运行有 8 个进程——配置里写哪个都不对。

**T｜我要解决的问题**

哪些并行变量属于「整组共享」，哪些属于「每个进程不同」？

**A｜我做了什么**

1. **按「是否全组相同」分类**：`PORRY_WORLD_SIZE`、task/run/attempt、路径，全组一份，可以进配置；`RANK` / `LOCAL_RANK` 每个进程一个，由 torchrun / launcher 在启动时设。
2. **把边界写进演示**：`translate.log` 第 4 段末尾那句「RANK / LOCAL_RANK 不在这里」。
3. **留出扩展位**：`RuntimeSpec` 只放「整组共享」的东西；每进程变量由启动器协议负责，这一课不展开。

**R｜结果**

配置里不会再出现「一份配置八个 RANK」的矛盾；排查并行问题时，知道去进程环境里看 RANK，而不是翻 ConfigVersion。

**可能被追问**

- 那 `MASTER_ADDR` 呢？——通常由 rendezvous / coordinator 决定，也不该由用户填；属于 Day 5 启动执行的范围。
- 平台完全不碰 RANK 吗？——平台可能校验「RANK 覆盖了 0..N-1 且不重复」，但值的来源是启动器。

**核句**

> 配置是「整组一份」的事实；每个进程不同的东西，属于启动器，不属于配置。

## 第三组：私有变量与保存语义

### Q7｜私有变量的出口与复制

**S｜我遇到的情况**

CLI 实跑里我传了 `hf_token=hf_real_value`，输出是 `hf_token *** ← run_override`。但 `ConfigVersion.merged` 里必须还是真值——不然容器起不来。这条「存真值、出口掩码」的分界，是这一课最实用的一条。

**T｜我要解决的问题**

哪些地方必须藏？哪些地方必须真？复制任务时怎么处理？

**A｜我做了什么**

1. **存储真值**：`merged` / RuntimeSpec 的 `env` 保留真值，执行时才连得上依赖服务。
2. **三个出口掩码**：页面与 API 响应、日志与事件 payload、复制任务（`mask_config`，`config.py:262`；`cli.py::_print_config` 已接）。
3. **识别规则**：显式名单 + 后缀（`_token / _key / _secret / _password …`），`is_secret()` 统一判断，`env` 里按变量名逐个掩。
4. **复制任务**：清空私有变量并要求重填，而不是复制一份——复制凭据等于绕过授权。

**R｜结果**

`test_secrets_masked_at_exit_but_kept_for_execution` 同时断言两件事：`spec.env["WANDB_API_KEY"]` 是真值，`spec.public()["env"]` 是 `***`；CLI 日志里 `hf_token` 显示 `***`。

**可能被追问**

- 掩码会不会让排障变难？——保留字段名和来源，值不可见；真要看值走审批与审计，而不是让所有人默认能看。
- 后缀规则会误伤吗？——会（比如 `monkey` 不是密钥），所以生产应改成「显式标注 + 默认不可见」，后缀只做兜底。

**核句**

> 私有变量的分界线不在「存不存」，在「出口给谁看」；复制任务应该重填，不应该复制。

### Q8｜平台给了路径 ≠ 代码用了路径

**S｜我遇到的情况**

有人反馈「数据没挂上」。我先看配置：`PORRY_DATA_PATH` 有值，挂载也在。再看训练日志：代码里读的是另一个写死的路径。平台这边全部正确，问题在「读」这一步。

**T｜我要解决的问题**

平台对「配置生效」能证明到哪一步？

**A｜我做了什么**

1. **把四问拆成两半**：前两问（设置、保存）和第三问（注入）平台能证明；第四问（读取）是训练代码的事。
2. **能做的验证**：启动前检查路径是否存在（算力/数据预检的一类）；启动后把实际 env 和挂载打进日志（观测课展开）。
3. **回答口径**：分层说——「平台已注入，代码是否读取需要看训练侧日志」；不把「我给了」说成「它用了」。

**R｜结果**

`translate.log` 第 3 段每个字段的「哪里读」都写清责任方；用户报「数据没找到」时，排查路径变成「先看 env，再看挂载，最后看代码」。

**可能被追问**

- 平台能不能强制代码读 env？——不能，只能约定 + 预检 + 观测；规范能写进镜像模板和启动脚本。
- 那平台的 KPI 是什么？——「给出的路径 100% 可达 + 可观测」，不是「代码一定用对」。

**核句**

> 平台能保证「变量在，路径可达」，保证不了「代码读了」——这两件事必须分开说。

### Q9｜保存 ≠ 保存并运行

**S｜我遇到的情况**

S3 的 `store` 里，`create_task` 和 `create_run` 本来就是两个调用。真正让我意识到差别的，是「保存成功但启动失败」这种情况：配置合法，资源不够，Run 卡在 pending——如果只有一个按钮，用户会以为「保存失败了」，然后反复提交。

**T｜我要解决的问题**

为什么要把这两个动作分开？合成一个会丢什么？

**A｜我做了什么**

1. **两个动作**：`create_task` 保存意图（可编辑、`rev`）；`create_run` 冻结配置并建 Run（可执行、不可变）。
2. **三种结果都能表达**：保存成功且运行成功 / 保存成功但运行失败（配置合法、资源或 gang 不满足）/ 保存失败（字段非法）。
3. **和状态机对上**：Run 的 `pending → scheduling → failed` 就是「保存成功但运行失败」的路径；`failed` 的 `reason` 里写清是资源还是 gang。

**R｜结果**

用户不会因为「启动失败」去改一个本来就正确的配置；平台也能把「配置错误」和「资源不足」分开统计。

**可能被追问**

- 那「保存并运行」按钮怎么做？——前端调两个接口，中间失败就停在「已保存、未运行」，并给出 Run 的失败原因。
- 保存失败会不会留下脏 Run？——不会，`create_run` 在 `save_config` 之后；字段校验应在 `save_config` 之前拦住非法值（本 toy 还没做 schema 校验，是缺口）。

**核句**

> 一个按钮回答不了两个问题：配置对不对、资源够不够；拆开才有确定的失败语义。

## 第四组：五条命门（速答卡）

**1. 五组字段，哪组不改变容器形状？**

身份 / 程序 / 输入 / 环境资源 / 保障观测。身份组和保障组不改变这次容器形状（但影响校验、通知与采集）。

**2. 四层优先级与 `None` 规则**

`template < task < run_override < platform_injected`；`None` 视为「这层没写」，不覆盖上层。

**3. 三条路径变量**

`PORRY_DATA_PATH`（数据，挂 `/data`）、`PORRY_CKPT_PATH`（产物，挂 `/ckpt`）、`PORRY_TF_EVENTS_PATH`（TensorBoard，默认在 ckpt 目录下）。

**4. 为什么 init 的 export 传不到 start**

两者是两次独立的 `sh -c`、两个进程；环境只来自平台注入，不回读上一个 shell。正路是写进 `env` 字段或直接写进 `start_cmd`。

**5. 私有变量的三个出口**

页面 / API 响应、日志与事件 payload、复制任务。存储保留真值，掩码只发生在出口。

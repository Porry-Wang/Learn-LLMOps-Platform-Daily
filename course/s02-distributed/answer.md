## 第一组：理论四问（D3.1）

### Q1｜gloo 和 nccl 的区别？为什么这台 Mac 只能用 gloo？换 backend 要改几行代码？

**S｜我遇到的情况**

第一次跑 `dist.py`，我用的是文档里最常见的 `backend="nccl"`，直接起不来。这台 Mac 是 Apple Silicon、没有 NVIDIA 卡。换成 `gloo` 之后 4 个 rank 正常打出结果。我需要搞清楚：这个替换改变了什么、又没改变什么，否则实验结论能不能用我心里没底。

**T｜我要解决的问题**

backend 到底负责哪一层？换掉它，「all-reduce 之后每个 rank 都拿到总和」这个结论还成立吗？

**A｜我做了什么**

1. **先把两层分开**：backend 是通信实现（走什么路），collective 是通信语义（做什么动作）。all-reduce 是语义，gloo / nccl 是它的两种实现。
2. **查清各自的适用面**：gloo 走 CPU + 以太网（TCP），macOS 上唯一可用；nccl 走 GPU，用 NVLink / InfiniBand / GPUDirect RDMA，只在 Linux + NVIDIA 卡上有。
3. **确认代码改动量**：`dist.all_reduce(t, op=SUM)` 一行都不用动，只改 `init_process_group(backend=...)` 里的一个字符串。这就是 PyTorch 把语义和实现分开的收益。
4. **划出验证边界**：gloo 能验证 rank、组、collective 的**语义正确性**，验证不了带宽、延迟、拓扑、超时行为。

**R｜结果**

4 个 rank 都拿到 `[10.0, 10.0, 10.0, 10.0]`，语义验证通过。但「跨机 TP 会掉 MFU」这类结论在 gloo 上跑不出来——这正是 Day 2 的 `capacity.py` 里 TP≤8 只能当**硬约束**、不能当通信代价来定价的原因。边界：换 backend 不改语义，改的是性能和你敢不敢下性能结论。

**可能被追问**

- 为什么 macOS 没有 nccl？——NCCL 依赖 CUDA，macOS 没有 NVIDIA 驱动。
- gloo 能传 GPU 张量吗？——能一部分，但没有 GPUDirect，走主机内存拷贝，性能不能拿来类比。

**核句**

> backend 是路，collective 是动作；换路不改动作，改的是你能不能谈性能。

### Q2｜rank / world_size / local_rank 各回答什么问题？为什么不能自己算 rank？

**S｜我遇到的情况**

`dist.py` 打印的是 `[rank 2/4 local_rank=2]`，我一开始以为这俩是同一个东西的两种写法——单机 4 进程时它们确实一一对应。直到看 README 里 16 卡的例子（`TP=2, PP=2, DP=4`）才发现完全不是一回事。

**T｜我要解决的问题**

三个编号各自回答什么问题？为什么代码里要读环境变量，而不是自己算？

**A｜我做了什么**

1. **world_size**：进程总数，`TP × PP × DP`。回答「这次训练一共几个进程」。
2. **rank**：全局编号 `0..world_size-1`，通信时用它标识身份。回答「我是这批进程里的第几个」。
3. **local_rank**：机内编号 `0..local_world_size-1`，用来选卡（`cuda:{local_rank}`）。回答「我在这台机器上是第几个」。
4. **为什么必须读环境变量**：`rank = machine_id × 8 + local_rank` 只是常见约定，不是保证。分配编号的人是 launcher（torchrun / K8s Training Operator），进程自己算就会和真实分组对不上。`dist.py` 里那两个 `assert dist.get_rank() == rank` 就是在强调「以库为准」。

**R｜结果**

实测注入的变量：`WORLD_SIZE=4`、`LOCAL_WORLD_SIZE=4`、`MASTER_ADDR=localhost`、`GROUP_RANK=0`。单机时 RANK 与 LOCAL_RANK 一一对应，看起来像同一个东西；一旦跨机，两台机器上**各有一套** local_rank 0–7，但 rank 是 0–15。分两层的原因也就清楚了：选卡是机内的事，通信是全局的事。

**可能被追问**

- local_rank 会重复吗？——会，而且必然重复：每台机器都有一套 0..7。
- 为什么要两个编号？——`cuda:{local_rank}` 只能在本机范围内选卡，用全局 rank 取模是错的（异构机型下每机卡数不同）。

**核句**

> rank 是全局身份，local_rank 是机内座位号；两者都该问 launcher，不该自己算。

### Q3｜all-reduce 和 reduce 的区别？DP 为什么必须用 all-reduce？

**S｜我遇到的情况**

写 `debug_dist.py` 段 1 的时候，我第一版写成「把 4 个张量加起来，结果给 rank 0」。跑出来只有 rank 0 手里是 10。但 `dist.py` 的真实输出是 4 行**都**是 10（见 `logs/dist.log`）。我的模拟和真实现语义不一致。

**T｜我要解决的问题**

两者差在哪？以及 DP 为什么不能用「reduce 到 rank 0 再 broadcast」这个看起来等价的方案。

**A｜我做了什么**

1. **定义差别**：reduce 是汇总到一个 root，只有 root 拿到结果；all-reduce 是汇总后**每个 rank 都拿到同一份结果**。
2. **回到 DP 的下一步**：all-reduce 之后每个进程要各自更新自己那份模型，所以每个进程都必须持有平均梯度。用 reduce 就得再补一次 broadcast，两次通信。
3. **写出等价实现**：all-reduce ≡ reduce-scatter + all-gather。reduce-scatter 让每个 rank 只拿到自己负责那一片的和，all-gather 再补齐——这也是 ZeRO 和 DDP 分桶通信的基础。
4. **确认一个易错点**：all-reduce 只归约、**不做平均**。SUM 之后是 10，不是 2.5；除以 world_size 是 DDP 自己做的第二步。

**R｜结果**

段 1 模拟输出 4 行 `after` 全是 `[10.0, 10.0, 10.0, 10.0]`，平均梯度 `[2.5, 2.5, 2.5, 2.5]`；段 2 里 `world_size=1` 时 all_reduce 前后不变（`[3,3,3,3]` → `[3,3,3,3]`），反证「加上别人」这一步确实由通信层完成，不是张量自己的性质。

**可能被追问**

- all-gather 和 all-reduce 区别？——all-gather 是拼接（结果变长），all-reduce 是归约（结果长度不变）。
- ZeRO-3 用哪个？——前向/反向之前 all-gather 分片权重，反向之后 reduce-scatter 梯度。

**核句**

> all-reduce = 每人都拿到汇总结果；DP 需要它，因为每个进程都要自己更新模型。

### Q4｜checkpoint 至少要存哪四样？各自丢了会怎样？

**S｜我遇到的情况**

`ckpt.py` 实验 2 的 C 组只存了 `model.state_dict()`。加载**没有报错**，续训第 32 步 loss 从 0.174 冲到 6.845。文件能打开、模型能加载，训练却废了。

**T｜我要解决的问题**

一个真正能续训的 ckpt 至少要有哪几样？每一样丢了分别付出什么代价？

**A｜我做了什么**

1. **`model.state_dict()`**——现在参数是多少。丢了就从随机初始化重来。
2. **`optimizer.state_dict()`**——Adam 的 m / v，以及每个参数的 step。丢了第一步退化成 `lr·sign(g)`，刹车消失。
3. **全局 step（或 token 数）**——在第几步。丢了 lr 调度回到 warmup、日志横轴归零、ckpt 排序错乱。
4. **config（结构 + 超参）**——模型是什么形状。丢了造不出空壳，权重没地方放。

**R｜结果**

A 组存全套，与不中断的对照组最大 loss 偏差 `0.00e+00`，逐位一致；C 组第 31 步 ‖Δθ‖=2.516，是 A 组 0.293 的 **8.6 倍**。要精确复现还得加 RNG 状态和数据游标（可选两样）。实测 ckpt 结构：6 个张量、5313 个参数、文件 70.5 KB。

**可能被追问**

- `optimizer.state` 的 key 为什么是数字不是参数名？——PyTorch 按 `param_groups` 里的顺序编号；这也是换模型结构续训会静默错位的坑。
- `param_groups` 要不要存？——要，lr 这些超参本身就在里面。不存的话续训时 lr 会回到你新建 optimizer 时写的值，而不是中断时的值。

**核句**

> 前两样决定「能不能接着算」，后两样决定「从哪一步、以什么形状接着算」。

## 第二组：代码追问三题（D3.2）

### Q5｜SUM 改成 MAX 之后，4 个 rank 的 after 是什么？为什么「不再需要加法」？

**S｜我遇到的情况**

`dist.py` 第 22–24 行留了个改动实验，要求先写下预测再跑。我第一反应是「MAX 之后每个 rank 拿到自己那份的最大值」，但立刻发现说不通——每个 rank 的张量四个元素都是同一个数，「自己的最大值」没有意义。

**T｜我要解决的问题**

MAX 归约的对象是「跨 rank」还是「跨元素」？结果为什么和 SUM 有本质区别？

**A｜我做了什么**

1. **确认归约方向**：collective 归约是**跨 rank** 的，对每个元素位置独立进行。rank 0..3 在同一位置上分别是 1、2、3、4。
2. **算 MAX 的结果**：每个位置取 4 个 rank 里的最大值 = 4，所以 4 个 rank 的 `after` 都是 `[4.0, 4.0, 4.0, 4.0]`。
3. **解释「不需要加法」**：MAX 是**选择型**归约，结果就是某个 rank 的原值，不产生新数；SUM 是**聚合型**，结果是所有 rank 共同算出来的新值。
4. **推回训练**：DP 必须用 SUM，因为只有求和才把 4 份不同数据的信息合进一个梯度。用 MAX 等于丢掉 3 份数据，4 张卡退化成 1 张卡的等效 batch。

**R｜结果**

预测 `[4.0, 4.0, 4.0, 4.0]`，实跑一致。`debug_dist.py` 段 1 把 SUM 的累加过程打印出来了：`[1,1,1,1]` → 加 rank1 → `[3,3,3,3]` → 加 rank2 → `[6,6,6,6]` → 加 rank3 → `[10,10,10,10]`（`logs/debug_dist.log`），单步能看清它是三轮加法。

**核句**

> SUM 产生新值，MAX 只是选出某个原值；DP 要的是前者。

### Q6｜去掉 `dist.barrier()` 会怎样？为什么这类 bug 最难查？

**S｜我遇到的情况**

`dist.py` 结尾是 `dist.barrier()` 然后 `destroy_process_group()`。我把 barrier 注释掉跑了几次，4 行输出看起来完全正常，于是差点认为这行是多余的。

**T｜我要解决的问题**

barrier 在这里防的到底是什么？为什么它「看起来没用」？

**A｜我做了什么**

1. **看进程之间的时间差**：rank 0 要多打一段环境变量，可能比别人慢；反过来也可能某个 rank 打印完就退出。4 个进程不是齐步走的。
2. **推先退出的后果**：先退的进程会销毁自己的进程组、释放 TCPStore 连接。此时别的 rank 还在通信里等它，就会报连接错误或 hang。
3. **理解 barrier 的角色**：它是一次「全员到齐才放行」的集合操作，保证所有人都不再通信了，才一起去销毁。它同步的是**退场**，不是计算。
4. **归到同一类规矩**：这跟 `init_process_group`、`new_group` 是一类东西——集合操作必须所有 rank 以**相同顺序、相同次数**调用，否则死锁。

**R｜结果**

4 进程小规模下大概率看不出问题，所以它是「预防性」的一行；规模一大、进程退出时间差一大，就会偶发报错。这类 bug 的特点是不稳定复现、日志里只有一个 rank 有异常，最难查。真实的 gang 语义就是从这里来的：一个 rank 失败，要让所有 rank 一起退。

**可能被追问**

- barrier 会永久卡住吗？——不会，有 `timeout`（gloo 默认 30 分钟），超时抛异常。
- 生产里怎么处理退出？——训练框架在退出前做 barrier + 错误传播；平台侧则靠 `role=trainer` 挂了就把整个 Run 判失败（S3 的 `ROLE_ON_LOST`）。

**核句**

> barrier 不是同步计算，是同步退场；集合操作必须全员同序调用。

### Q7｜C 组的 ‖Δθ‖ 为什么是 A 组的 8.6 倍？

**S｜我遇到的情况**

实验 2 里 C 组第 31 步 ‖Δθ‖=2.516，A 组 0.293。只说一句「optimizer 状态丢了、刹车没了」我不满意——我要能用公式把这个数算出来，否则面试里被追一层就没了。

**T｜我要解决的问题**

Adam 的更新量公式是什么？m、v 清零后第一步退化成什么？2.516 这个数从哪来？

**A｜我做了什么**

1. **写出公式**：`Δθ = lr · m̂ / (√v̂ + ε)`，其中 `m̂ = m/(1-β₁^t)`、`v̂ = v/(1-β₂^t)`。
2. **代入清零后的第一步**：`m = (1-β₁)g`、`v = (1-β₂)g²`，偏差修正恰好把它们还原成 `m̂ = g`、`v̂ = g²`。
3. **得到退化形式**：`Δθ = lr · g/(|g|+ε) ≈ lr · sign(g)`。**梯度大小被完全丢掉**，每个参数不管梯度是 1e-6 还是 1.0，都迈满 `lr = 0.05`。
4. **核对数量级**：模型 5313 个参数，但第 31 步只有 **2536 个梯度非零**（另外 2777 个在死掉的 ReLU 单元后面，梯度恰好是 0，所以不动）。`0.05 × √2536 = 2.5179`，实测 `‖Δθ‖ = 2.5164`，**相对误差 0.06%**——公式几乎精确命中。这也解释了为什么不是 `0.05 × √5313 = 3.64`。

**R｜结果**

第 32 步 loss 从 0.174 冲到 6.845。更重要的方法论收获：**‖Δθ‖ 比 loss 早一步报警**。只看 loss 要等到第 32 步才看见爆炸，看 Δθ 第 31 步就抓到了——所以 `run_steps()` 同时记录两者，不是冗余。

（2536 这个数可以自己核：在 `run_steps()` 里 `optimizer.step()` **之前**加一行统计
`sum(int((p.grad != 0).sum()) for p in model.parameters())`。注意必须在 step 之前数，
参数一动，ReLU 的存活集合就变了，数出来会是另一个值——我第一次就数错了。）

**可能被追问**

- 普通 SGD 会有这个问题吗？——无动量的 SGD 不会（它直接用 g）；带 momentum 的一样会丢 m。
- A 组为什么能逐位一致？——数据预生成 + 种子固定 + 单进程。真实流式数据 + 多卡归约的浮点顺序，通常做不到逐位一致，判据要退成「曲线在误差带内接上」。

**核句**

> 丢了 optimizer 状态，Adam 第一步退化成 `lr·sign(g)`；‖Δθ‖ 比 loss 更早报警。

## 第三组：五条命门（闭卷速答）

**1｜`world_size = TP × PP × DP`：三个维度各切什么？**

S/T（一行）：要说清 16 卡布局里「每个进程到底拿到什么」，否则放置和通信代价都无从谈起。

A：**DP 切数据**——每份拿完整模型副本 + 1/N 的 batch，每步通信一次，能跨机；**PP 切层（depth）**——每份拿模型的一段 stage，每个 micro-batch 收发激活，能跨机但气泡变大；**TP 切同层内部（width）**——每份拿这层参数/激活的一个切片，每层多次通信，一般不能跨机，必须待在 NVLink 域内。

R：三者切的**对象不同**所以能相乘；`2×2×4 = 16 = world_size`。

> 核句：DP 切数据、PP 切深度、TP 切宽度。

**2｜建组规则一句话说出来。**

S/T（一行）：同一个 rank 要同时属于三张网，得有个确定的编号规则。

A：`rank = dp_idx × (PP×TP) + pp_idx × TP + tp_idx`；建组规则只有一条——**三个坐标固定两个，让第三个遍历**。16 卡 TP2/PP2/DP4 时：TP 组 `{0,1} {2,3} … {14,15}`（8 组×2 人，本机内）；PP 组 `{0,2} {1,3} … {13,15}`（8 组×2 人，本机内）；DP 组 `{0,4,8,12} … {3,7,11,15}`（4 组×4 人，**必然跨机**）。成员身份靠 `dist.new_group(ranks=[...])` 显式建，所有 rank 必须以相同顺序调用相同次数。

R：布局决定哪张网是「本机」的。换一种展平顺序，DP 组会变连续，但 TP 组就跨机了。

> 核句：切法决定分几份，放置决定通信代价。

**3｜backend vs collective，各举两例。**

S/T（一行）：Q1 已经分清两层，这里要求能报出具体名字和常用组合。

A：backend 是通信实现——`gloo`（CPU/以太网）、`nccl`（GPU/NVLink/IB）；collective 是通信语义——all-reduce、all-gather、reduce-scatter、broadcast、send/recv。常用组合：**DP 梯度** all-reduce（等价于 reduce-scatter + all-gather）；**ZeRO-3 权重** 前向/反向之前 all-gather 分片、反向之后 reduce-scatter 梯度；**TP** 前向一次 all-reduce 合并部分和、反向再来一次；**PP** 用 `send/recv`，**不是集合通信**。

> 核句：backend 是路，collective 是动作；PP 是唯一不用集合通信的。

**4｜启动七步里哪三步对应 Day 2 的三个时刻？**

S/T（一行）：Day 2 说「资源就绪 / 程序启动 / 训练真正开始」是三件事，要在七步里指出它们的位置。

A：第 **1** 步（资源与上限：机器数、单机卡数、NVLink 域、配额）= 资源就绪；第 **4** 步（launcher 拉起进程并注入 `RANK / LOCAL_RANK / WORLD_SIZE / MASTER_ADDR`）= 程序启动；第 **7** 步（各自装载代码/配置/数据/ckpt，出现 **first loss**）= 训练真正开始。中间第 5 步 `init_process_group` 是集合操作，缺一个就 hang；第 6 步 `new_group` 建 TP/PP/DP 句柄。

R：第 2 步的四条校验——`tp·pp·dp == 卡数`、`tp ≤ 单机卡数`、`tp | heads`、`pp ≤ layers`——正是 S1 `capacity.py` 里 `feasible_placements()` 的硬约束，一字不差。

> 核句：卡到位 ≠ 进程起来 ≠ 训练开始，三件事分开看，判据是 first loss。

**5｜`state_dict` 里没有什么？加载顺序是什么？**

S/T（一行）：实验 3 的报错说明 state_dict 不足以重建模型。

A：`state_dict` 只有「名字 → 张量」，**没有结构信息**。所以顺序永远是：**config 造空壳 → `load_state_dict` 填数据**。实验 3 把 hidden 从 64 改成 128，再用同一个 state_dict 加载，立刻 `size mismatch for net.0.weight: copying a param with shape torch.Size([64, 16]) … current model is torch.Size([128, 16])`。

R：config 只保证「装得进去」，代码 commit 才保证「装对了」——pre-LN 和 post-LN 参数名完全一样、形状也一样，能加载，但语义不同。

> 核句：state_dict 是数据不是结构；能装进去 ≠ 装对了。

## 第四组：动手实验的两个口头解释（D3.3）

### Q8｜`world_size=1` 时 all_reduce 前后不变，这个「空转」实验证明了什么？

**S｜我遇到的情况**

`dist.py` 必须由 torchrun 拉起 4 个子进程，PyCharm 的断点打在父进程上，子进程里的断点停不下来——我想单步看 all-reduce，但没法调。于是我写了 `debug_dist.py`，段 2 里把 `world_size` 设成 1，结果 all_reduce 前后张量一模一样。第一反应是「这个实验白跑了」。

**T｜我要解决的问题**

一个什么都没改变的实验，到底提供了什么信息？它的失效边界在哪？

**A｜我做了什么**

1. **把它当反证用**：段 1 里 `total` 从 1 加到 10，是我用 for 循环手工加的；段 2 里同样调 `dist.all_reduce`，只有自己时结果不变。两边对照，说明「加上别人」那部分确实是**通信层**做的，不是张量运算自带的性质。
2. **暴露 API 的调用顺序**：注入环境变量 → `init_process_group` → 通信 → `barrier` → `destroy_process_group`。单进程下这套顺序能完整走通，断点每一行都能停。
3. **拆分两类问题**：它顺带验证了 gloo 在这台机器上可用（不经 torchrun 也能建组），把「环境能不能跑」和「多进程协同对不对」两个问题分开——macOS 上 `getfqdn` 那个坑属于前者。
4. **写明失效边界**：`world_size=1` 验证不了「多个进程互相等」，也就是验证不了 gang 语义；那必须回到 4 进程看 `logs/dist.log`。

**R｜结果**

单进程能断点单步，4 进程只能看打印输出。这个取舍是有意的：**可观测性和真实性在这里不可兼得**，所以分两段做，各拿一半。段 3 里还留了真 4 进程的调试路径（PyCharm 勾 `Attach to subprocess automatically while debugging`，run config 指向 `torchrun_local.py`），但能不能停下来取决于 PyCharm 版本，我没验证过，所以写成「试」而不是「行」。

**核句**

> 空转实验不是白跑，它是把「通信做的」和「代码做的」分开的对照组。

### Q9｜为什么说「config 只保证装得进去，代码 commit 才保证装对了」？

**S｜我遇到的情况**

实验 3 的 `size mismatch` 很直观，把 hidden 改回 64 就好了。但我随即意识到：形状对得上、名字也对得上的情况下，`load_state_dict` 一样会成功——而那时可能是错的。

**T｜我要解决的问题**

`load_state_dict` 到底检查什么、不检查什么？不检查的那部分靠什么防？

**A｜我做了什么**

1. **列出它做的两件事**：按名字找张量、按形状复制。名字对上、形状对上，它就返回成功。
2. **指出它不做的事**：不检查语义。pre-LN 和 post-LN 的 LayerNorm 位置不同，但参数名（`layers.0.ln_1.weight` 这一类）可以完全一样，形状也一样。
3. **推演后果**：加载成功、不报任何错，训练却静默跑偏——loss 可能还在降，只是降不到该有的位置。这类 bug **没有异常可抓**，只能在流程上防。
4. **给出防法**：ckpt 的 manifest 里记代码版本（git commit）、config、并行布局。换 commit 续训要先比对，不能直接加载。

**R｜结果**

这就是 README 里「平台第 9 节产物链路」要求记 manifest 的原因。落到 S3 的代码上：`Artifact` 里 `manifest` 是一个独立字段，不是可选装饰；`kind` / `path` / `checksum` 只能回答「文件在不在、坏没坏」，回答不了「这是哪份代码产出的」。

**核句**

> shape mismatch 会报错，语义 mismatch 不会——不报错的那个更贵。

## 第五组：业务映射（D3.4）

### Q10｜平台第 6 节「启动执行」和第 9 节「产物链路」对应今天的哪个实验？平台故意不做什么？

**S｜我遇到的情况**

S2 的两个实验都跑在单机上，4 个进程或者 1 个进程，完全没有平台参与。但 README 要求做平台映射。我得说清对应关系，尤其是**平台不做什么**——否则「平台什么都能管」这种话听起来就像黑盒。

**T｜我要解决的问题**

两个实验分别落到平台的哪一节？平台的能力边界划在哪，划错会怎样？

**A｜我做了什么**

1. **第 6 节 ← `dist.py`**：launcher 负责注入 rank 环境变量、拉起 N 个进程。平台的边界是——**不替训练程序做 collective，也不替 Infra 决定 TP/PP/DP**。
2. **平台真正能做的是提交时校验**：`tp·pp·dp == 卡数`、`tp ≤ 单机卡数`、`tp | heads`、`pp ≤ layers`。校验不过就拒绝，不让它进 scheduling。这就是 S1 `feasible_placements()` 的落点。
3. **第 9 节 ← `ckpt.py`**：ckpt 只有带 `.done` 标记才算完整；manifest 要记 step / config / 并行布局 / 代码版本，否则换卡数续训时无法重新分片。
4. **观测上的一条**：续训后曲线「断崖」多半是横轴从 0 重算，不是训练真崩了——这是「图正常 ≠ 训练正常」的一个具体例子，也是 Q7 里 step 必须存的原因。

**R｜结果**

平台在这两节里都是「**记录 + 校验 + 展示**」，不是「替训练做决定」。这条边界划错，平台就会变成一个谁都不敢用的黑盒：算法同学不知道为什么被拒，Infra 同学不敢把切法交给它。反过来，只做校验和登记，两边都能自己解释结果。

**核句**

> 平台管准入和产物登记，不管 collective 和切法选择。

### Q11｜为什么 Run 的结束状态要拆成三个独立字段？

**S｜我遇到的情况**

C 组的进程退出码是 0，`.pt` 文件也能 `torch.load` 成功。按任何单一指标看，这次运行都算「成功」。但续训第 32 步 loss 冲到 6.845。

**T｜我要解决的问题**

Run 的结束状态该记什么？为什么不能用一个 bool？

**A｜我做了什么**

1. **拆成三个字段**：`exit_code`（训练进程怎么退的）、`ckpt_state`（`none` / `partial` / `complete`，产物写完了没）、`loadable`（文件能不能读回来、形状对不对）。
2. **验证它们互相不能推导**：退出码 0 不代表 ckpt 写完（最后一步 save 可能被截断）；ckpt 完整不代表能加载（config 对不上）；能加载也不代表续训质量合格（**C 组就是**）。
3. **落到模型定义上**：S3 的 `Run.fully_succeeded` 要求三个同时成立；`ckpt_state` 用三值而不是 bool，就是为了区分「没写」和「写了一半」——后者意味着目录里有残留，清理逻辑不一样。
4. **落到平台行为上**：三个都成立才把 Artifact 标为可续跑；否则界面要显示「退出 0 但 ckpt 不完整」，让用户自己决定要不要重试，而不是替他判成功。

**R｜结果**

C 组在这个模型里是 `exit_code=0, ckpt_state=complete, loadable=True`，三个都成立，但续训质量不合格——说明**三个成功也只是必要条件，不是充分条件**。真实系统还得看第四个：续训后 loss 接不接得上。这一步平台做不了（要等下一次运行才知道），只能把 ‖Δθ‖ 和 loss 曲线的数据摆出来给用户看。

**核句**

> 三个成功互相不能推导，所以必须分开记；合起来也只是必要条件。

### Q1｜16Ψ 的 16 是哪五项加起来的？为什么 FP16 训练反而比 BF16 更容易溢出？

**S｜我遇到的情况**

写 `capacity.py` 第一版时，我按“一个参数 2 字节”估显存，7B 算出 14 GB，觉得单卡 80G 绰绰有余。但所有人都说 7B 单卡训不动。这个账对不上，说明我漏了东西。

**T｜我要解决的问题**

训练时每个参数到底要预留多少字节？为什么不是 2（权重），也不是 4（FP32）？

**A｜我做了什么**

1. **把五项列出来对账**：BF16 权重 2 + BF16 梯度 2 + FP32 主权重 4 + Adam 动量 m 4 + Adam 方差 v 4。
2. **搞清为什么要 FP32 主权重**：BF16 尾数只有 7 位，参数更新量很小时会被直接舍掉；所以更新在 FP32 副本上做，做完再转回 BF16 供前向。
3. **比较 FP16 和 BF16**：FP16 只有 5 位指数，最大约 65504，大梯度/大激活容易溢出成 inf；BF16 有 8 位指数，范围约 3.4e38，和 FP32 同级。
4. **确认代价**：BF16 尾数比 FP16 少，所以用“BF16 权重梯度 + FP32 主权重”的组合，拿 16 字节/参数换稳定。

**R｜结果**

16 字节/参数，7B 模型仅模型状态就是 `7e9 × 16 = 112 GB`，单卡 80G 必然 OOM——账终于对上了。顺带纠正一个常见说法：FP16 不是“精度低”，它的尾数反而比 BF16 多一位，输的是指数范围。边界：这 16 是**训练时**的账，纯推理只存权重，7B 在 BF16 下是 14 GB。

**可能被追问**

- 只存 BF16 主权重行不行？——小更新会被舍掉，训练后期几乎不收敛。
- m 和 v 为什么不能合并？——量纲不同，一个在分子一个在分母。

**核句**

> 16 字节买的是稳定训练；FP16 输在指数范围，不是精度。

### Q2｜激活公式里 34 和 5as/h 分别对应什么？为什么 attention 那一项和 s² 成正比？

**S｜我遇到的情况**

我把 `capacity.py` 的序列长度从 8k 调到 32k，模型状态没变，激活却从几 GB 涨到几十 GB，直接把预算顶爆。我需要知道：到底是哪一项在涨，砍哪一项最划算。

**T｜我要解决的问题**

把激活公式拆开，找出随序列长度超线性增长的那一项，并判断它能不能被重算换回来。

**A｜我做了什么**

1. **拆 34**：它是所有随 `s·b·h` 线性增长的激活——attention 输入、QKV 投影、输出投影，MLP 输入、4h 中间层、激活缓存、输出。论文口径可粗拆成 attention 线性 10 + MLP 线性 24；它不是物理常数，会随融合算子和 mask 存法变化。
2. **拆 `5as/h`**：分数矩阵是 `a×s×s`，每个分数存 5 字节（分数 2 + softmax 输出 2 + dropout mask 1），总量 `5as²b`；除以 `sbh` 得 `5as/h`。
3. **确认 s² 的来源**：QK^T 里每个 query token 都要和每个 key token 算一次相似度，所以分数矩阵是 `s×s`；序列翻倍，它变 4 倍。
4. **算取舍**：长序列下平方项远大于 34，而重算 attention 的 FLOPs 占比很小；selective 砍掉平方项（单层 `34sbh`），full 更激进（只留 `2sbh`），代价是算力账从 `6ND` 变 `8ND`。

**R｜结果**

按 `s=8192, a=64, h=8192` 代入：`5as/h = 320`，是 34 的近 10 倍；序列到 32k 就是 1280。所以长序列下砍平方项最划算——省的是显存，付的是少量重算算力。边界：34 不是定理，换实现会变；而且激活按 `layers/pp/tp` 切，不按 dp 切。

**可能被追问**

- 为什么重算 attention 便宜？——它是显存大头，但 FLOPs 占比小。
- 32k 能不开 recompute 吗？——单层平方项就到几百倍 34，基本必然 OOM。

**核句**

> 34 是线性项，`5as/h` 是 attention 的 `s²` 项；s 越长，`s²` 越贵。

### Q3｜ZeRO-3 相比 ZeRO-1 省了多少显存、多了多少通信？为什么通信是 1.5×？

**S｜我遇到的情况**

7B、8 卡、单卡 80 GB：模型状态 112 GB，ZeRO-0 直接爆。我把候选缩到 ZeRO-1 和 ZeRO-3，想知道多花的通信到底换回多少显存——这个交换不量化，选型就只能靠感觉。

**T｜我要解决的问题**

两者差多少显存、差多少通信，以及什么情况下这笔交换不划算。

**A｜我做了什么**

1. **写公式对比**：ZeRO-1 每卡 `(4Ψ + 12Ψ/dp)/(tp·pp)`；ZeRO-3 每卡 `16Ψ/(tp·pp·dp)`。
2. **算差值**：相减得 `4Ψ(1 - 1/dp)/(tp·pp)`；7B、tp=pp=1、dp=8 时是 38.5 GB → 14 GB，省 24.5 GB。
3. **算通信**：ZeRO-1 每步约 2Ψ（梯度 reduce-scatter + 更新后权重 all-gather）；ZeRO-3 约 3Ψ（前向前 all-gather 权重、反向前再一次、反向后 reduce-scatter 梯度），3/2 = 1.5。
4. **找边界**：dp=1 时没有可切的分片，收益为零，只剩通信开销。

**R｜结果**

8 卡下省 24.5 GB、多 1.5× 通信。判断标准不是“谁更省显存”，而是省下来的显存能不能换到更大 batch 或更长序列——换不到就是白付带宽。边界：ZeRO-3 省的是模型状态，**不省激活**，长序列 OOM 时它可能一点忙都帮不上。

**可能被追问**

- 为什么不直接上 ZeRO-3？——通信多 50%，小规模省不出对应收益。
- ZeRO-2 在哪一档？——梯度也切，`(2Ψ + 14Ψ/dp)`，通信与 ZeRO-1 同量级。

**核句**

> ZeRO-3 用 1.5× 通信换掉最后一份 4Ψ 复制；省的是模型状态，不是激活。

### Q4｜为什么 TP 一般不超过 8？（提示：NVLink 域；用 D1 学过的一句话说明「跨机 TP」在 reconcile 视角下会让哪本账变难看）

**S｜我遇到的情况**

写 `--scan` 时，我一开始没限制 TP，结果它给我推荐了 `tp=16`，算出来的有效时长漂亮得不真实。原因很简单：我的公式里只有算力和气泡，**没有跨机带宽这一项**。

**T｜我要解决的问题**

TP 的上限该定在哪，以及为什么这个限制必须写进准入而不是只写在注释里。

**A｜我做了什么**

1. **看通信频率**：TP 在每一层内部做 All-Reduce/All-Gather，前向反向都要同步；DP 只在梯度更新时通信，差一个数量级。
2. **找物理边界**：一台 8 卡机器通常就是一个 NVLink 域；tp 超过单机卡数就要走 InfiniBand，带宽降、延迟升，MFU 明显掉。
3. **承认例外**：有 NVLink 交换机或机柜级互联时可以跨机，但成本和复杂度高；本课程列为不推荐。
4. **用 reconcile 视角补一刀**：一个 TP 组是一个不可分割的逻辑副本。跨机后它横跨多台机器，任何一台故障，整个组一起重启——故障域从“一台机器”变成“一组机器”，容量账、故障账、重试账都要重算。

**R｜结果**

`tp ≤ 单机卡数` 写进准入校验，`--scan` 不再产出跨机 TP 的候选。代价是显性的带宽 + 隐性的故障域；这也是为什么 70B 更愿意用 TP8 封顶、靠 PP 和 DP 扩出去。

**可能被追问**

- 8 是魔法数字吗？——不是，是“一台机器几张卡”这个物理事实，换 NVL72 这类机柜级域会变。
- 70B 怎么跑？——TP=8 封顶，剩余用 PP + DP，再配 ZeRO。

**核句**

> TP 的通信在每一层，必须待在 NVLink 域；8 卡一台是物理边界，不是拍脑袋。

### Q5｜手算：1000 张 H100、7B、1T token、MFU 0.4，训练要多久？再用脚本验证（单位陷阱：B 和 T 之间差几个零？）

**S｜我遇到的情况**

第一次手算，我得出“29.5 分钟”，还觉得挺合理。直到把结果和脚本对账，发现差了两个数量级——我把 7B 当成了 7，把 1T 当成了 1。

**T｜我要解决的问题**

把单位摊平重算一遍，并把这条容易错的换算固化进脚本，避免下次再错。

**A｜我做了什么**

1. **先摊单位**：`N = 7B = 7e9` 个参数，`D = 1T = 1e12` 个 token；`N×D = 7e21`。B 和 T 之间差 `1e18`（1e9 × 1e12）。
2. **套公式**：`C = 6ND`；`hours = C / (gpus × peak_tflops × 1e12 × mfu) / 3600`。
3. **代入**：`C = 6 × 7e9 × 1e12 = 4.2e22` FLOPs；有效算力 `1000 × 989e12 × 0.4 = 3.956e17` FLOP/s；时间 `≈ 1.062e5` 秒。
4. **和脚本对账**：手算与 `capacity.py` 输出一致，都是 29.5 小时。

**R｜结果**

约 **29.5 小时**，这是纯算力下界。边界：989 是 BF16 **稠密**峰值，1979 是 2:4 稀疏，不能拿来算稠密 `6ND`；没计气泡、通信、数据加载和故障重启，真实排期要按 1.2–1.5 倍备。

**可能被追问**

- 为什么是 6ND？——前向 2 + 反向 4；重算再加 2 变 8。
- 能拿这个数承诺业务吗？——不能，它是下界，还要叠加排队和故障率。

**核句**

> `6ND` 先把 B 和 T 展开成“个”，再除以卡数×峰值×MFU；29.5 小时是下界。

## 第二组：业务映射栏（写进 README.md 最后一节）

### Q6｜平台表单只收「机器数 × 单机卡数」，切法到底谁定？平台该提供什么、校验什么？

**S｜我遇到的情况**

做准入设计时，我发现一个尴尬：表单上只有“几台机器、每台几张卡”两个数，但这两个数根本不足以决定 TP/PP/DP/ZeRO。我得先想清楚，这两条信息到底够干什么，缺的那部分该由谁补。

**T｜我要解决的问题**

划清平台和 Infra 的边界：谁决定切法，平台在这件事上不可省略的职责是什么。

**A｜我做了什么**

> 先纠正一个常见题干：平台不替 Infra 决定 TP/PP/DP/ZeRO。切法依赖模型结构、框架和通信拓扑，Infra 最清楚，也必须显式写进脚本/配置，保证可复现、责任清晰。

1. **明确平台能提供什么**：单机卡数、GPU 型号与 HBM、NVLink 域、可用机器数、队列/配额、拓扑与亲和性——这些是 Infra 做决策的输入。
2. **把三本账做成计算器**：Infra 填完切法，平台能立刻算出每卡显存、气泡占比、有效时长。
3. **在提交时做准入校验**：`tp·pp·dp = 总卡数`、`tp ≤ 单机卡数`、`tp | heads`、`pp ≤ layers`、`m ≥ 2pp`、不 OOM；坏配置当场拒绝，而不是等运行时炸。
4. **留证据**：保存配置版本、放置方案、rank 映射、事件时间线，失败时能回答“当时为什么这么切、哪本账超了”。

**R｜结果**

那两个数只给出上限：一共几张卡、TP 最多能到几。切法由 Infra 写进配置，平台负责算后果、拦坏配置、留证据。边界：平台可以给推荐值，但不能把推荐当成用户改不动的默认值。

**可能被追问**

- 为什么不让平台自动选？——切法依赖模型结构和框架实现，猜错的代价是跑几小时后 OOM。
- 平台至少该做什么？——准入校验 + 容量计算 + 记录，这三件就够有价值。

**核句**

> 切法由 Infra 写，平台把资源和后果算清楚：提交前拦住跑不了的，运行时暴露跑得慢的，事后留下可复盘的证据。

## 第三组：五条命门（闭卷速答）

### 1｜`16 = 2 + 2 + 4 + 4 + 4`，各是什么？

**S/T**：估显存时按参数个数乘字节，问的是这 16 字节的构成。

**A｜我是这么记的**

- BF16 权重 2 字节（前向计算用）
- BF16 梯度 2 字节（反向传播用）
- FP32 主权重 4 字节（更新时保持精度，避免 BF16 抹掉小变化）
- Adam 动量 m 4 字节（优化器历史）
- Adam 方差 v 4 字节（优化器历史）

**R｜结果**：2+2+4+4+4 = 16 字节，7B 就是 112 GB。

**记忆钩子：权重梯度各 2，主权重 4，动量方差各 4。**

### 2｜设 `Ψ` 为参数个数，写出 ZeRO-0/1/2/3 的每卡模型状态公式。

**S/T**：单卡装不下，问的是每一档能切掉哪部分。

**A｜我是这么推的**

```
ZeRO-0：16Ψ / (tp·pp)
ZeRO-1：(4Ψ + 12Ψ/dp) / (tp·pp)
ZeRO-2：(2Ψ + 14Ψ/dp) / (tp·pp)
ZeRO-3：16Ψ / (tp·pp·dp)
```

- **4Ψ（权重+梯度）**：前向和反向时**每张卡都要用完整的一份**，所以不能切。
- **12Ψ（FP32 主权重 + m + v）**：只在**参数更新时**用，且**每个参数的更新是独立的**（`weight -= lr * m / sqrt(v)`），所以能按 dp 切。

**R｜结果**：能切的，恰恰是“只在更新时用、且每参数独立”的；不能切的，恰恰是“前向反向必须完整”的。

**记忆钩子：前向反向要用的不切，只在更新时用的才切。**

### 3｜激活为什么只切 TP（和 PP）、不切 dp？`s²` 项从哪来？

**S/T**：长序列 OOM 时，问的是激活该往哪个维度上分。

**A｜我是这么理解的**

- **dp 的每张卡跑不同的 micro-batch**，激活本来就是各自独有的数据，**不存在重复**，没有“复制”可省。
- **TP 把同一层的计算拆到多张卡**，同一份激活被拆开，每张卡只算自己那部分，**所以要除以 TP**。
- `s²` 来自 QK^T：每个 query token 都要和每个 key token 算一次相似度，分数矩阵是 `a×s×s`。

**R｜结果**：dp 切数据，激活天然不同；TP 切模型，激活被拆开，所以要除 TP。

**记忆钩子：dp 切数据，激活天然不同；TP 切模型，激活被拆开。**

### 4｜`6ND` 的单位陷阱是什么？full recompute 为什么变成 `8ND`？

**S/T**：估训练总量时，问的是 6 和 8 从哪来、单位怎么展开。

**A｜我是这么算的**

- **6ND = 前向 2ND + 反向 4ND**
  - 前向：每个参数每个 token，1 次乘 + 1 次加 = 2 次浮点运算 → 2ND
  - 反向：算对输入的梯度（2 次）+ 算对权重的梯度（2 次）= 4 次 → 4ND
- **8ND = 6ND + 重算前向 2ND**：full recompute 在反向时要把前向重新算一遍，多烧 2ND。
- **单位陷阱**：`N = 7B = 7e9`，`D = 1T = 1e12`，两者差 `1e18`；先把 B/T 展开成“个”。

**R｜结果**：6 = 2 + 4；full 再加一次前向 = 8。

**记忆钩子：普通 6ND，full 8ND，多出来的 2 是重算的前向。**

### 5｜`--scan` 的排序键为什么不能是“是否 OOM”？

**S/T**：扫出几十个可行配置，问的是拿什么指标排序。

**A｜我是这么选的**

- “不 OOM”只是及格线；能进候选的都不 OOM，再按它排序没有区分度。
- 两个都不 OOM 的配置，有效时长可能差 30% 以上。
- 排序键应该是吞吐 ∝ `1 / (时长 / (1 - 气泡占比))`，即“时长 × 气泡惩罚”越小越好。

**R｜结果**：先筛掉 OOM 的，再在及格线里选有效时长最短的。

**记忆钩子：OOM 是及格线，吞吐才是分数。**

## 第四组：排序与准入（Q7）

### Q7｜`--scan` 的排序键为什么不能是「是否 OOM」？

**S｜我遇到的情况**

`--scan` 第一版我按“显存占用”排序，觉得省内存最安全。结果它给我推了一套 TP4/PP1/DP32 + full 的方案，一算有效时长 3072 小时；而另一套 TP8/PP1/DP16 + selective 只要 2304 小时——**我按显存排出来的“最优解”，比真实最优慢了 33%**。

**T｜我要解决的问题**

换一个排序键，让它真的在“能跑的方案里挑最快的”，并且能处理同分情况。

**A｜我做了什么**

1. **确认 OOM 只是门槛**：它是二元的，只回答“能不能跑”；能进候选的都不 OOM，再按它排序没有区分度。
2. **改用吞吐**：两个都不 OOM 的配置，有效时长可能差 30% 以上。
3. **定排序键 `hours/(1-bubble)`**：折算成无气泡的等效时长，越小越快；同分再按小 TP、小 PP、省显存 tie-break。
4. **用反例验证**：70B/128 卡，TP8/PP1/DP16 + selective 是 52.97 GB、2304 h；TP4/PP1/DP32 + full 是 77.90 GB、3072 h。

**R｜结果**

先按 OOM 过滤，再按等效时长升序。反例里两套都能跑，但一套 2304 h、一套 3072 h——按“是否 OOM”排是完全看不出差别的。边界：等效时长不含排队和数据加载；pp=1 时气泡为 0，公式退化成 hours 本身。

**可能被追问**

- 为什么不直接按显存排？——那是在选“最不容易 OOM”，不是选“最快”。
- 气泡怎么算？——`(pp-1)/(m+pp-1)`，工程上要求 `m ≥ 2pp`。

**核句**

> OOM 是及格线，吞吐才是分数；先筛掉跑不了的，再在及格线里选有效时长最短的。

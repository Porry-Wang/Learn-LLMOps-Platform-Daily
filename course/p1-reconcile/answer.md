## 第一组：理论四问（D1.1）

### Q1｜命令式和声明式的区别？K8s 为什么选声明式？

**S｜我遇到的情况**

我写 `reconcile_loop.py` 的第一版时，用的是最直觉的写法：观察一次，缺几个补几个，补完退出。跑通之后我做了个实验——把循环里的 `pass` 改成 `break`，让它在第 6 轮就结束。结果很安静：没有报错，结尾还打印了 `✅ 3/3`，但第 10 到 30 轮的五次扰动，一次都没人处理。

**T｜我要解决的问题**

问题不在“循环怎么写”，而在于：**进程退出之后，谁还记得“应该 3 个”？** 我得先想清楚，这套接口到底交付“步骤”还是交付“目标”，否则后面所有的自愈都无从谈起。

**A｜我做了什么**

1. **先把两种接口分开**：命令式给过程（先 A 再 B），声明式只给目标（我要 3 个），过程归控制器。
2. **用 break 实验验证差别**：中断之后，命令式脚本没有留下“还差什么”的记录；而声明式的期望值一直躺在存储里，谁都能重新读一遍。
3. **把“故障是常态”写进设计前提**：机器坏、网络抖、配置被改，都是会发生的；只有持续对比现实，系统才能收敛。
4. **顺着推到产品形态**：用户只填核心参数，执行复杂度被封装——这正是“页面填表发起训练”能成立的前提。

**R｜结果**

选声明式。证据是那组对照：break 版第 6 轮退出后，5 次扰动全部无人处理；保留循环的版本，5 次扰动都在下一轮被修复。代价是单次反应可能多一轮观察，不保证立即收敛。

**可能被追问**

- 会不会更慢？——单次可能多一轮观察，换来可恢复和可审计，故障常态下这笔交换划算。
- 期望状态存哪？——K8s 在 etcd 的 spec 里；平台里就是任务表单和配置版本。

**核句**

> 命令式是一次性指令，声明式是一份长期合同。

### Q2｜`act()` 有 30% 失败率，为什么系统最终还能收敛到 3 副本？

**S｜我遇到的情况**

循环写好了，但 toy 里 `act()` 从来没有失败过，这让我不放心——真实的创建请求会因为限流、节点不足、网络抖动失败。于是我给它加了 30% 的随机失败，想看看循环会不会被“卡死”在半路。

**T｜我要解决的问题**

在这种成功率下，期望 3 副本还能不能达标？如果能，是靠什么机制，前提又是什么？

**A｜我做了什么**

1. **确认它每轮都重新观察**：循环不记“上次做到哪”，只比较当前期望和当前现实。
2. **确认失败没有改变现实**：创建失败后，差额仍然是 1，下一轮会重新生成同一个动作。
3. **算概率**：单次失败只推迟达标；在独立假设下，连续 10 次都失败的概率是 `0.3^10 ≈ 0.000006`。
4. **验证归零后的行为**：差额为 0 时 `diff` 返回空列表，系统什么都不做——所以做一百遍和做一遍结果相同。

**R｜结果**

系统能收敛，但这是**概率意义**上的收敛，不是有限步保证。实验里 `--fail-rate 0.5`（一半会失败）时，只要事件不丢，副本仍然补到了 3。边界也很清楚：真实故障往往相关（同节点、同网络），独立假设一破，收敛会明显变慢，所以生产上要配退避、重试上限和告警。

**可能被追问**

- 失败率 100% 呢？——不收敛，非零成功率是前提。
- 重试会不会造成风暴？——会，所以要有退避、限流和熔断；循环本身不解决这个问题。

**核句**

> 单轮失败只推迟达标，阻止不了达标，因为循环每一轮都重新从现实出发。

### Q3｜spec 和 status 为什么要分开？合并成一个字段会出什么问题？

**S｜我遇到的情况**

写 toy 的存储时，我图省事，只用一个 dict 记状态：`{"a": "Running", "b": "Running"}`。跑通之后我试着把它换成单字段版本——把“期望副本数”和“当前副本数”放同一行，控制器补完一次就把实际值写回去。

**T｜我要解决的问题**

这两个值到底该不该分开？如果合成一个字段，会在哪一步坏掉？

**A｜我做了什么**

1. **先看作者**：期望值只由用户写，实际值只由控制器写；合成一个字段，两边写入会互相覆盖。
2. **再看信息**：“期望 3、实际 2”这个差额本身是信息，是 reconcile 的驱动力，也是告警和页面状态的数据源。
3. **确认流向**：控制器按期望修正现实，绝不把观察结果写回期望——实际分配到的节点 IP 不该混进用户模板。
4. **做反证**：单字段版本里，控制器把 2 写回去，下一轮目标就变成了 2，永远补不齐。

**R｜结果**

必须分开。分开后“期望 − 实际”才是可计算的差额；这正是 K8s 把 spec 和 status 分成两个字段的原因，也是我在 toy 里保留 `expected` 和 `observed` 两个 dict 的原因。

**可能被追问**

- status 能不能被用户改？——API 层可能允许，但语义上归控制器；改了也不改变期望。
- 为什么不用事件代替 status？——事件是流水，status 是快照；恢复和展示需要快照。

**核句**

> spec 是愿望，status 是现实，系统的全部工作就是把两者的差额变成动作。

### Q4｜边缘触发丢一个事件后为什么无法自愈？真实系统怎么补救？

**S｜我遇到的情况**

D1.5 我想验证“事件驱动是不是更省”，于是写了 edge 版：只在 `changed` 非空时运行。然后我故意在第 3 轮丢掉一条 Pod 死亡事件。结果是——第 4 到 30 轮，动作数全是 0，最终停在 0/3。日志我存成了 `exp5_drop3_fail05.log`。

**T｜我要解决的问题**

为什么没有崩溃、没有报错，却永远修不好？以及工程上靠什么兜住这种情况？

**A｜我做了什么**

1. **确认它的工作方式**：edge 不轮询，它的“世界观”完全由事件流构建。
2. **还原那一轮发生了什么**：Pod 死亡和缓存销账同时发生，`changed` 从此为空；期望和现实的缺口还在，但触发条件消失了。
3. **把损失说准**：不是少响应一次，而是**失去了发现出错的手段**。
4. **找补救**：框架层的定期全量 resync（informer 按周期把对象重新推一遍），加上“差额持续不为零就告警”，兜住 resync 周期内的静默窗口。

**R｜结果**

单靠事件无法自愈。我还跑了个对照——丢事件发生在第 30 轮（`exp5_drop30_control.log`），前面一直正常；这说明 edge 不是永远坏，**事件不丢时它更快**，坏的时候是“你看不见”。分工是：事件负责快，resync 负责不漏。

**可能被追问**

- resync 能完全替代事件吗？——能兜底但延迟高。
- 为什么不在每次事件里全量对账？——那就变成 level-triggered，edge 省成本的优势消失。

**核句**

> 丢事件丢掉的不是一条通知，是未来任何一天发现自己出错的能力。

## 第二组：代码追问三题（D1.2）

### Q5｜`diff()` 里数 Running 时，如果把状态过滤去掉、直接数 dict 里所有 key，什么场景下会算错？

**S｜我遇到的情况**

`diff()` 第一版我写得很省事：`len(observed)`。toy 里所有用例都绿了，因为 toy 的约定是“死了就删记录”，所以过滤和不过滤没有区别。这个“全绿”让我警觉——它可能只是测试太顺。

**T｜我要解决的问题**

在什么场景下这个简化会算错？错的是哪一层语义？

**A｜我做了什么**

1. **把记录分成两类**：运行中/可用的，和已失败但记录还没删除的。
2. **推演数量被高估的后果**：差额被低估甚至归零，控制器在可用不足时不补建，系统带病却自认为达标。
3. **把 toy 扩展成“失败标记不删除”**：这一改，差异立刻显形。
4. **对照 K8s 的做法**：Deployment 统计的是 Ready 副本数，不是 Pod 对象总数。

**R｜结果**

要数“可用对象”，不是“存在对象”。具体例子：期望 3，有 3 条记录但 1 条 Failed——不过滤判定达标，实际只有 2 个可用端点，该补的 1 个永远不会补。

**可能被追问**

- `phase=Running` 为什么不够？——Running 不等于 Ready，进程活着未必能接流量。
- Terminating 算不算可用？——通常不算，要看业务是否允许优雅退出期间继续接流量。

**核句**

> 数对象和数可用对象是两个数字，把“存在”当成“可用”是状态失真的经典源头。

### Q6｜edge 实验里 Pod 明明死了，为什么后面 27 轮都是「动作 0」？把因果链一步步讲出来。

**S｜我遇到的情况**

跑 edge 实验时，我盯着日志看了很久：Pod 已经死了，期望还是 3，但后面 27 轮每一轮都是“动作 0”。没有异常，没有告警，程序跑得很“健康”。

**T｜我要解决的问题**

把这条因果链一步步讲清楚：为什么“一切正常”的运行日志，对应的却是一个永远修不好的系统？

**A｜我做了什么**

1. **确认控制器不直接看世界**：它只在“现实与记录出现差异”时被触发，这个差异就是 `changed`。
2. **还原丢事件那一轮**：Pod 死亡与记录销账同时发生，`changed` 不再产生；缓存与现实一致，但期望与现实的缺口还在。
3. **推演静默如何变永久**：无 `changed` → 无事件 → 无 observe/diff/act；世界也没有新变化，系统就停在 0/3。
4. **做对照实验**：如果只删现实、不删记录，差异会持续存在，事件即使迟到也能让系统自愈。

**R｜结果**

缺口一直在，只是没有任何机制去观察它。对照实验说明了关键一点：**致命的不是事件迟到，是差异被掩盖**。真实系统靠 watch 断点续传（resourceVersion）加定期 resync 来兜底。

**可能被追问**

- 是不是信号被压制？——不是，没有任何信号被压制，产生信号的对比根本没发生。
- 真实系统怎么避免？——resourceVersion 续传 + 定期 resync + 差额告警。

**核句**

> 27 轮不是信号被压制，是产生信号的物理过程已不存在。

### Q7｜如果把 `act()` 改成「失败就自动重试直到成功」，外面那个循环还有什么存在意义？

**S｜我遇到的情况**

为了处理偶发失败，我给 `act()` 加了“失败重试直到成功”。加完之后我一度想：既然动作最终一定会成功，外层那个每轮 observe/diff 的循环是不是可以删了？

**T｜我要解决的问题**

验证这个想法：重试能不能替代循环？如果不能，边界在哪？

**A｜我做了什么**

1. **先分清对象**：重试对的是“这份动作清单”，循环对的是“目标”。
2. **引入变化**：重试正在创建 Pod A 时，Pod B 死了，用户还把期望从 3 改成 4。
3. **观察重试的反应**：它仍然只创建 A，因为它手里的清单是旧的。
4. **观察循环的反应**：下一轮看到 4 vs 2，重新生成两个动作。

**R｜结果**

不能替代。差别不在“试几次”，而在**信息来源**：重试只看旧清单，循环看世界。重试仍然值得保留（处理瞬时失败、减少空转），但必须有上限、退避和幂等保证，否则会卡死循环。

**可能被追问**

- 能不能只在循环里重试？——可以，但重试逻辑仍要基于最新观察，本质还是循环。
- 重试和幂等什么关系？——幂等让重试安全；不幂等的动作重试会重复副作用。

**核句**

> 重试忠于动作清单，循环忠于目标与现实。

## 第三组：词汇检查（D1.3）

### Q8｜集合推导式 `{name for name, state in observed.items() if state == "Running"}` 的三部件各干什么？

**S｜我遇到的情况**

这是 `diff()` 里我读得最慢的一行。它不是业务逻辑，但读错一个部件，后面“数几个、删哪个”就全错，所以我单独拆开看了一遍。这一题没有业务冲突，我不硬编场景。

**T｜我要解决的问题**

四个部件各负责什么？它和后面的计数、删除分别是什么关系？

**A｜我做了什么**

1. **`observed.items()`**：提供此刻每个条目的（名字，状态）键值对，已删除的不包含。
2. **`for name, state in ...`**：把每对解包成两个变量，逐个遍历。
3. **`if state == "Running"`**：只保留运行中的条目。
4. **开头的 `name`**：决定放进结果的是名字，不是状态；结果集合交给 `diff` 去计数和挑删除对象。

**R｜结果**

它只负责“收集名字集合”，计数和删除是 `diff` 的事。举个数：`{"a":"Running","b":"Failed","c":"Running"}` 得到 `{"a","c"}`，长度 2。

**可能被追问**

- 为什么用集合？——去重 + O(1) 成员判断，代价是丢顺序。
- 两个 Pod 同名怎么办？——K8s 名字唯一；toy 用 dict 也保证唯一。

**核句**

> 推导式四零件各管各的——从哪拿、怎么拆、留什么、装什么进结果。

## 第四组：动手实验的两个口头解释（D1.4–D1.5）

### Q9｜（D1.4）把 `pass` 改成 `break`、跑 `--disturbance 5` 后，为什么日志里根本看不到 💥 那行？

**S｜我遇到的情况**

我想验证“达标就退出”行不行，于是把第 118 行的 `pass` 改成 `break`，跑了一遍扰动实验。日志干净得可疑：一个 💥 都没有，结尾还体面地打印了 `✅ 3/3`。

**T｜我要解决的问题**

这个“一切正常”的结果，到底证明了什么？能不能据此说系统没问题？

**A｜我做了什么**

1. **核对轮次**：扰动设在第 10/15/20/25/30 轮，而 break 版第 6 轮就退出了，那些轮次根本没发生。
2. **拆开那句 ✅**：它描述的是退出瞬间的状态，与“之后一直保持 3/3”没有逻辑关系。
3. **区分两种“什么都不做”**：巡视版的“不做”是每轮对比后确认无差额；退出后的“不做”是根本没做对比。
4. **推演真实系统**：控制器退出后，没有任何实体知道“应该 3 个、现在几个”，故障会无日志、无告警地发生。

**R｜结果**

日志空白不代表没故障，只代表**观测窗口被截短**了。对照结果是：break 版 0 次扰动、第 6 轮退出（`exp4_quit.log`）；巡视版满 30 轮、5 次扰动全部被修复（`exp4_keep_looking.log`）。

**可能被追问**

- 那什么时候可以退出？——目标一次性完成且不再需要保证时；长期系统不行。
- 怎么证明“之后也能保持”？——只能靠持续运行或定期核对，退出后的打印证明不了。

**核句**

> 退出后打印的成功验证的是过去，控制器的职责是未来——两者没有逻辑关系。

### Q10｜（D1.5）「丢事件就下班」和「达标就 break」为什么是同一个错误的两种写法？

**S｜我遇到的情况**

两个实验做下来，两段完全不同的代码，最后都停在了错误状态：break 版停在第 6 轮之后再无动作，丢事件版停在 0/3。我把两份日志并排看，越看越像同一个东西。

**T｜我要解决的问题**

判断它们是两个独立的 bug，还是同一个设计错误的两种表现。

**A｜我做了什么**

1. **比后果**：两者都让“实际持续符合期望”失去保证。
2. **比机制**：切断的是同一个东西——发现差异的信息来源；break 是主动放弃对比，丢事件是被动掩盖差异。
3. **挖共同假设**：都默认“正确会自行延续”；而分布式系统里，现实持续偏离才是常态。
4. **对照正确设计**：对比不因达标而停止（level-triggered），发现不依赖通知送达（resync 兜底）。

**R｜结果**

是同一类错误，区别只在可观测性：break 至少是显式选择，丢事件更隐蔽。所以修复方向也只有一句话：让“发现差异”这件事，既不依赖当前状态，也不依赖消息一定送达。

**可能被追问**

- 哪个更危险？——丢事件更隐蔽，break 至少还是人做的决定。
- resync 能救 break 吗？——不能，进程都退出了，没人执行 resync。

**核句**

> 达标退出和只等报信是同一种赌法——赌世界不会在你不在场时改变。

## 第五组：业务映射（D1.6）

### Q11｜Reconcile Loop 这套机制在 PorryLLMOps 平台里对应什么功能？给算法/Infra 同学解决什么痛点？如果这层抽错了会怎样？

**S｜我遇到的情况**

对着训练平台的九张截图梳理对象时，我发现容错那一节的动作用词几乎能一一对上：检测 → 判定 → 选 checkpoint → 重启 → 验证。这跟 D1 的 observe → diff → act 是同一个形状。而现实中，算法同学提交任务后要盯几小时到几天，Infra 靠人肉看板和人肉重启兜底。

**T｜我要解决的问题**

把这套机制准确地映射到产品上：它对应哪个功能、给两类人分别解决什么、抽错了会退化成什么。

**A｜我做了什么**

1. **分界面**：页面填参数 = 写期望；平台采集 rank 存活、心跳、日志、指标 = 读实际。
2. **指认机制本体**：容错调度链路就是循环——对比差额（少了一个 rank）+ 执行修复（重启缺失 rank、驱逐坏节点）。
3. **找产品证据**：热更新的“下一次容错生效”，说明配置变更正是靠这个循环传播进运行中的任务。
4. **列抽错的三种坏法**：观察值回写用户模板（作者混淆）；只靠上报不做核对（页面显示运行中、实际挂死，GPU 空烧）；发现差额却没有修复动作（退化成大屏）。

**R｜结果**

平台的真正价值不在“提交成功那一刻”，而在提交之后几千小时里每一次偏离都被发现和纠正。所以这层最容易的退化，就是做成一块只展示、不修复的大屏——看着专业，值守一点没省。

**可能被追问**

- 和 K8s controller 的区别？——对象不同（训练任务/rank vs Pod），动作不同（重启 rank、回滚 checkpoint、驱逐节点），循环范式相同。
- 平台最容易被抽错成什么？——大屏，只展示状态不执行修复。

**核句**

> 平台卖的不是提交那一刻，是提交之后几千小时里每一次偏离都被发现和纠正。
